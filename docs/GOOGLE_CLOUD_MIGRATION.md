# 영차 Google Cloud 이전 계획

작성일: 2026-10-21 (한국 시간).

진행 기록: [Google Cloud 이전 진행 기록](GOOGLE_CLOUD_PROGRESS.md).
사용자는 300달러 크레딧으로 이전을 우선 진행하도록 요청했다. 예산 알림 설정은
초기 진입의 필수 조건에서 뒤로 미루고 테스트 배포 준비를 시작한다. 크레딧 종료
후 정상 월 비용을 확인하고 기존 운영비 상한을 지키는 원칙은 유지한다.

### 2026-10-22 변경 — 기존 테스트 데이터 가져오기 생략

Google 테스트 배포 성공 후 사용자가 기존 데이터는 모두 테스트용이고 보존할
필요가 없으며 다시 입력하겠다고 명시했다. 따라서 아래 계획의 원본 DB 추출·
복원·이력 비교·원본 서명 키 전달은 실행 대상에서 제외한다. 현재 Google DB를
그대로 사용해 카카오 로그인, 신규 회원의 운영자 권한, 새 카페/메뉴/판매자 연결을
설정한다. 이전 Railway 연결 코드와 권한을 Google 계정에 재사용하지 않는다.
원본 데이터 가져오기는 완료가 아니라 **사용자 결정으로 생략**한 것이다.
이 결정만으로 Railway 자원 삭제·서비스 종료를 실행하지 않는다. 앞으로의 실제
주문 이력 보존 원칙은 유지한다. 아래 원본 보존 절차는 결정 이전 계획으로 남긴다.

사용자가 Railway에서 Google Cloud로 이전하기로 결정하고 이전 계획 작성을 요청했다.
이번 작업은 현행 구조 확인과 계획 수립이다. 아직 Google Cloud 자원 생성·결제·
데이터 이전·주소 전환은 실행하지 않았다. 기존 제품 기획은 유지하며 기능 개발
7단계보다 이전 작업을 우선한다. 한 단계씩 완료 결과를 보고한다.

## 확인된 출발점

- Django/Python, PostgreSQL, HTML/CSS/JavaScript, Docker를 사용한다.
- `scripts/start_web.sh` → `scripts/run_services.py`가 웹과 기한 처리 프로그램을
  함께 감독한다. 한 프로세스가 종료되면 컨테이너가 실패하도록 구성돼 있다.
- `run_deadlines`는 기본 5초 간격으로 DB에 저장된 기한을 검사한다.
  요청 처리 중에도 관련 주문의 기한을 검사한다. 브라우저가 열려 있어야만
  작동하는 구조가 아니다.
- 공개 사이트는 5단계다. 6단계 판매자 조회·수락·거절은 로컬 구현과
  153개 테스트·실제 300초 검증을 마쳤지만 Railway 배포에 실패했다.
  이 기록은 Google Cloud 환경의 검증을 대신하지 않는다.
- Railway DB는 이전 확인 기준 PostgreSQL 18이다. 실제 추출 직전에 버전과
  마이그레이션 적용 상태를 다시 확인한다. 대상 버전은 원본과 같거나 높은
  버전 중 실제 지원되는 것으로 선택하고 복원 시험을 통과해야 한다.
- 계획 수립 당시 Git 브랜치에는 커밋이 없고 소스는 미추적 상태였다. 이후
  이전 준비에서 비밀값을 제외한 소스를 커밋하고 GitHub의 별도 이전 브랜치로
  백업했다. 실제 실행 결과와 백업 범위는 진행 기록을 참고한다.
- 현재 관리 환경에는 Google Cloud 연동 권한이 관측되지 않았다. Railway 토큰
  바인딩은 준비돼 있지만 최근 프로젝트/배포 API는 인증을 거부했다.
  원본 DB를 추출할 수 있는 권한과 연결 경로 확보는 별도의 필수 조건이다.
- 사용자는 Google Cloud에 아직 가입하지 않았다고 답했다. 이전 1은 기존 Google
  계정을 이용한 Google Cloud 가입 안내부터 진행한다. 계정 가입만으로 작업 환경에
  Google Cloud 배포 권한이 자동 연결됐다고 간주하지 않는다.
- 월 운영비 상한은 기존 합의인 5만 원이다. Google Cloud의 최신 견적은
  아직 조회하지 않았으며 특정 구성의 예산 충족을 확정하지 않는다.

## 권장 구성과 비용 결정

첫 검토안은 Cloud Run + Cloud SQL이다. Django와 PostgreSQL은 그대로 사용한다.

| 구성 | 담당하는 일 | 계획 |
| --- | --- | --- |
| Cloud Run | 영차 사이트와 기한 처리 프로그램 실행 | 인스턴스 기반 과금·요청 외 CPU 사용·최소 인스턴스 1개를 전제로 검토한다. 정확한 설정과 가용성은 생성 전 확인한다. |
| Cloud SQL for PostgreSQL | 계정·카페·메뉴·주문·이력 보존 | 같은 지역, 자동 백업과 실제 복원 검증. DB 공개 접속을 무제한 허용하지 않는다. |
| Artifact Registry | 배포할 프로그램 묶음인 이미지 보관 | 버전별 이미지 식별자를 남겨 재배포·복구에 사용한다. |
| Cloud Build | 코드로부터 이미지 생성·검증 | 사용자가 승인한 버전의 배포를 반복 가능한 명령으로 만든다. 매 수정마다 운영으로 자동 반영하지 않는다. |
| Secret Manager | 카카오 Secret·Django 비밀키 등 보관 | 채팅·Git·이미지·로그에 넣지 않는다. 가능한 경우 장기 서비스 계정 키 파일 대신 Google 관리 인증을 사용한다. |
| Cloud Logging / Monitoring | 오류와 서비스 동작 점검 | 웹 응답·DB 연결·기한 처리 실패·재시작을 확인한다. 로그 보관량도 비용에 포함한다. |
| Cloud Storage | DB 이전 파일·별도 백업 보관 | 비공개·암호화·접근 제한. 백업 보유기간과 복구 방법을 함께 정한다. |

초기 후보 지역은 한국 사용자와 가까운 서울이다. 해당 지역의 제공 기능·전체
가격을 확인한 뒤 확정한다. 상시 실행 웹, DB, 백업/저장공간, 네트워크,
빌드/이미지/로그, 환율·세금을 포함해 무료 크레딧 종료 뒤의 정상 월 비용으로
계산한다. 이전 기간의 Railway와 Google 동시 비용도 별도로 표시한다.
예산 알림은 요금 차단 장치가 아니므로 사용량·최대 인스턴스·보관 정책도 설정한다.

관리형 구성이 월 5만 원을 넘으면 자원을 만들기 전에 비용표를 제시한다.
대안은 Compute Engine 한 대에 웹·기한 처리·PostgreSQL을 두고 영구 디스크,
별도 백업, HTTPS, 자동 재시작을 구성하는 것이다. 이 경우 OS·DB 업데이트와
복구 책임이 커지고 한 서버 장애가 웹과 DB에 함께 영향을 준다. 비용을 낮추기
위해 관리 부담을 늘리는 결정을 사용자에게 알리지 않고 실행하지 않는다.

## 단계별 실행과 완료 조건

| 이전 단계 | 작업 | 완료 조건 / 사용자 확인 |
| --- | --- | --- |
| 이전 1. 원본 보존·계정·견적 | 비밀값 제외 소스 백업, Google 계정/프로젝트/결제와 작업 권한 확인, 원본 DB 접근 확인, 주소 선택과 전체 견적 작성 | 소스가 작업 공간 밖에도 보존됨을 확인. 원본 DB 추출 경로와 대상 버전 호환성 확인. 비용표와 사용할 구성을 보고한다. |
| 이전 2. Google 테스트 환경 | 선택한 구성 생성, 비밀값·DB 연결·HTTPS·상시 기한 처리·로그 설정. 복제 데이터와 테스트 계정을 운영과 분리 | 테스트 주소에서 웹/DB 동작. 방문자가 없을 때와 컨테이너 재시작 후에도 기한 처리 확인. 기존 Railway 주문을 변경하지 않는다. |
| 이전 3. 복원 연습·6단계 검수 | 원본 DB의 안전한 복사본 복원, 대상 DB에 0006/0007 적용, 카카오 테스트 주소 추가, 세 역할과 전체 주문 흐름 검증 | 복원된 이력/권한/금액/고정 메뉴판/보호 함수·트리거 일치. 실제 5분·30분 및 수락/거절 검증. 사용자 본인 계정으로 확인할 테스트 주소 제공. |
| 이전 4. 최종 데이터 이전·주소 전환 | 짧은 점검 시간 확보, 이전 원본의 모든 쓰기 중지, 최종 백업·복원·검증, 새 환경을 유일한 운영 원본으로 지정 | 최종 백업 이후 누락 주문이 없음. 카카오 로그인·카페 영업 상태·새 공유 링크·기한 처리 정상. 새 주소를 사용자에게 전달한다. |
| 이전 5. 안정화·Railway 종료 | 새 환경 운영 로그/오류/비용 확인, 재배포·백업 복원 연습, 기존 환경 보존 후 종료 | 복구 가능한 백업과 배포 버전 확보, 합의한 관찰 기간 정상 동작 및 사용자 확인 후 Railway 자원을 정리한다. |

이전 단계 완료마다 실제 결과와 남은 문제를 보고한다. 기존 제품 개발 7단계의
PC 반복 소리·소리 테스트·일반 웹 알림은 이전과 6단계 사용자 확인 이후
별도 진행한다. APNs/FCM 앱 푸시 결정은 유지한다.

## 기한 처리와 배포 방식

- 현재 웹+기한 처리 감독 구조를 첫 후보로 재사용해 변경 범위를 줄인다.
  요청이 없을 때 CPU가 멈추거나 인스턴스 수가 0이 되는 구성을 사용하지 않는다.
  초기에는 일반 실행 인스턴스 수를 작게 제한하고 비용·DB 연결 수를 확인한다.
- Cloud Run의 최소 1개 설정도 무중단 실행을 보장하지 않는다. 재시작·배포 중
  중복 실행·인스턴스 교체를 시험한다. 기존 DB 행 잠금 기반의 중복 방지를
  유지하고 기한 처리 실패/지연을 운영 로그와 모니터링으로 감지한다.
- 기한은 DB에 저장된 원래 시각을 사용한다. 재시작·이전 시 5분/30분을 새로
  시작하지 않는다. 중단 중 지난 기한은 새 환경 시작 시 처리한다. 정상 실행의
  5초 검사 간격과 장애 시 지연 가능성을 구분해 기록한다.
- DB 구조 변경은 실행 중인 웹의 매 시작마다 하지 않는다. 새 웹 전환 전에
  단일 마이그레이션 작업으로 실행하고 성공 여부를 확인한다. Cloud Run 선택 시
  같은 이미지의 일회성 Job 등 실행 방법을 구성하고 기한 루프는 시작하지 않는다.
- 검증 → 이미지 생성 → DB 변경 → 새 버전 배포 → HTTPS/로그 점검을
  반복 가능한 명령으로 만든다. 배포 기록에는 이미지 식별자·소스 버전·
  마이그레이션·실제 점검 결과를 남긴다.

## 데이터 이전과 복구

1. 원본 DB 접근 가능 여부부터 확인한다. 현재 Railway 관리 API가 거부하는
   상태라면 다른 정상 승인 경로로 DB에 접근할 수 있는지 확인한다. 접근 가능한
   원본 백업을 확보하지 못했으면 기존 데이터 보존 이전은 진행할 수 없다.
2. 원본 버전에 맞는 `pg_dump`로 일관된 백업을 만든다. 실제 비밀번호나 연결
   문자열을 명령 출력·채팅에 노출하지 않는다. 파일 해시와 생성 시각을 기록하고
   접근을 제한한다. 더 낮은 PostgreSQL 버전으로의 복원을 전제하지 않는다.
3. 복원할 때 원본 플랫폼의 소유자/권한을 그대로 요구하지 않도록 역할을
   매핑한다. 회원·카카오 식별자·역할·카페·메뉴·옵션·주문·이력·시퀀스·
   제약·PL/pgSQL 함수와 보호 트리거를 포함해 검사한다. 행 수만 맞추는 것으로
   완료 처리하지 않는다. 최종 주문/메뉴판 사본·금액·기한의 대표값과 해시를
   비교하고 원본의 0005 이후에는 대상에 0006/0007을 적용한다.
4. 복원 연습 DB는 운영으로 사용하지 않는다. 연습 이후 최종 이전을 위한
   깨끗한 대상 DB에 최종 백업을 복원한다. 연습 중 생성된 주문·변경된 상태를
   최종 원본에 섞지 않는다.
5. 최종 이전은 점검 시간을 정하고 총무/참여자/판매자/운영자 및 로그인·로그아웃의
   변경까지 포함해 모든 원본 쓰기를 차단한다. 기존 기한 처리 프로세스도
   중지한 뒤 최종 스냅샷을 만든다. 가능한 경우 대기 주문을 먼저 정상 종료하도록
   안내하고, 남은 주문의 기한은 변경하지 않는다. 점검 시간은 복원 연습으로
   측정한 뒤 안내하며 지금 무중단이나 완료 시간을 약속하지 않는다.
6. 새 운영 DB 검증 후 새 웹·기한 처리만 쓰기를 허용한다. 구 환경은 쓰기
   금지로 유지해 두 DB에 주문이 나뉘지 않도록 한다.
7. 전환 전 실패는 새 환경을 닫고 원본을 재개할 수 있다. 새 환경에서 주문을
   받기 시작한 이후에는 오래된 Railway DB로 단순히 되돌리지 않는다. 새 DB의
   데이터를 보존한 채 호환되는 이전 프로그램으로 복구하거나, 다시 쓰기를
   중지하고 최신 데이터를 역이전하는 절차가 필요하다. DB 구조를 자동으로
   되돌려 주문 이력을 잃는 방식은 사용하지 않는다.

## 주소·카카오 로그인·회원

- Railway의 `*.up.railway.app` 주소는 Google로 소유권 이전할 수 없다.
  Google 테스트 주소 또는 별도 구매한 개인 도메인이 필요하다. 도메인 소유 여부와
  구매 비용은 이전 1에서 확인한다. 도메인 구매는 별도 결정 사항이다.
- 기존 카톡 공유 링크가 자동으로 새 서버로 이동한다고 약속하지 않는다.
  기존 원본을 수정할 수 있으면 읽기 전용 안내/안전한 리디렉션을 준비한다.
  불가능하면 새 주소로 다시 공유한다. 주문 기록과 링크 토큰 자체는 DB에 보존한다.
- 기존 카카오 개발자 앱을 재사용한다. 새 테스트/운영 주소와
  `/accounts/kakao/login/callback/`을 해당 로그인용 REST API 키 설정에 추가한다.
  기존 설정은 전환 검증 전 삭제하지 않는다. `KAKAO_RESET_API_KEY`는 사용자가
  정한 변수 이름 그대로 유지하고 값은 REST API 키다. Secret과 구분한다.
- 기존 카카오 사용자 식별자와 계정 연결코드·판매자/운영자 권한을 보존한다.
  주소가 달라지면 브라우저 로그인 쿠키를 옮길 수 없어 재로그인이 필요할 수
  있지만 새 회원가입이나 새 권한 연결이 필요한 이전 방식으로 만들지 않는다.
- Django 비밀키는 안전하게 전달하고 현재 서명된 링크/전송 확인에 대한 영향을
  검증한다. 키를 바꾸는 경우 서명 유효성 영향부터 확인한다. 비밀값은 Git에
  저장하지 않는다. 기존 지역 시간 Asia/Seoul과 DB 원본 시각을 유지한다.
- 판매자 로그인=영업 시작, 로그아웃=영업 종료라는 기존 결정을 유지한다.
  이전한다고 카페를 임의로 영업중으로 바꾸거나 연결 감지를 추가하지 않는다.

## 이전 완료 판정

- Google 주소의 홈, 정적 글꼴/로고, `/health/live/`, `/health/ready/` 정상.
- 실제 카카오 계정의 총무·연결 판매자·운영자 권한 정상, 참여자 정보 비노출.
- 방 생성→참여→총무 수정→마감→전송→판매자 수락/거절→총무 결과 전체 검수.
- 실제 300초 자동 거절·30분 미전송 폐기·수락/취소 경합·기한 보존 확인.
- 기존 주문/이력/금액/메뉴판 사본 보존과 수정 방지, 데이터 복원 시험 성공.
- 방문자가 없는 동안과 재시작 후에도 기한 처리, 배포 버전 복구 확인.
- 예상 비용·결제 알림·백업·최종 사용 주소와 남은 한계를 사용자에게 보고.
- Railway를 종료하기 전 사용자 실제 화면 확인과 최신 백업 확보.

현재 남은 확인: Google Cloud 계정·결제 프로젝트·작업 권한, 실제 견적,
원본 DB 추출 경로, 원하는 도메인 여부. 기존 구현의 재작성은 필요하지 않으며
이 문서 작성만으로 인프라 구성이나 데이터 이전이 완료된 것은 아니다.
