# 5단계 — 최종 전송·취소·5분 자동 거절

사용자가 5단계 시작을 승인했다. 판매자의 수락/거절·완료시간 입력은 6단계, 반복 소리·일반 웹 알림은 7단계에 남긴다. 이 단계의 대기 화면은 DB 처리 상태를 자동 조회한다.

## 사용 흐름

1. 화면 상단에 카페명과 주소 / 전화번호를 표시한다. 주문 패널의 첫 줄에 ‘[HH:MM] 주문서’와 ‘링크 복사’를 두며 실제 링크 주소는 숨긴다. 그 아래에는 건수 없이 ‘총 N잔’과 새로고침 아이콘을 나란히 표시하고 오른쪽에 총액을 둔다. 별도 링크 행과 카페 연락처 아래의 중복 만료 안내는 없다. ‘주문자 · 주문 메뉴 · 메뉴별 금액 · 수정’을 메뉴당 한 행으로 표시한다. 한 사람이 여러 메뉴를 주문하면 이름을 반복한 여러 행이 된다. 수량·총액을 유지하며, 참여를 마감하면 같은 화면에 ‘주문서 전송’ 버튼이 나타나고 별도 확인 화면을 거치지 않는다. 주문이 없으면 전송할 수 없다.
2. 전송 버튼 위에 카페에 메뉴·옵션·수량·금액과 총무 닉네임만 전달되며, 총무 전화번호와 참여자 이름(닉네임) 등 개인정보는 전달되지 않는다는 안내를 표시한다.
3. ‘주문서 전송’을 누르면 서버가 화면에 표시했던 주문과 현재 내용을 다시 비교하고, 현재 영업중인 카페에 한해서 최종 합산 주문서를 저장한다. 주문서를 연 뒤 주문/버전이 바뀌었으면 409로 주문서를 다시 열게 한다. 같은 전송을 재시도해도 한 건만 저장하고 전송 시각·5분 기한을 연장하지 않는다.
4. 전송 후에는 원래 주문과 카페용 합산 주문서를 누구도 편집/삭제할 수 없다. 주문방 삭제·새 항목 추가·참여자 제출도 차단한다. 상태와 처리 이력은 계속 추가된다.
5. 수락 대기 중에는 총무가 ‘주문 취소’를 누를 수 있다. 수락 또는 거절·취소 이후에는 취소할 수 없다. 취소해도 주문 내용·전송 시각·취소 이력은 보존한다.
6. 전송 시각부터 정확히 5분을 수락 기한으로 저장한다. 기한이 지나면 DB에서 `rejected`로 변경하고 `5분 미응답` 사유와 처리 시각·이력을 기록한다. 원래 주문방의 30분 폐기는 전송 이후 적용하지 않는다.
7. 열린 대기 화면은 상태 API를 5초 간격으로 조회하고 거절/취소 등으로 바뀌면 페이지를 갱신한다. 요청에서도 기한을 검사한다. 연결 오류에는 재확인 안내를 표시하고 복구 시 다시 조회한다. 앱 푸시나 판매자 소리는 아직 아니다.

## 구조와 보호

- `FinalOrder`는 주문방당 하나이며 총무 닉네임·합산 메뉴 사본·수량·금액·전송 시각·수락 기한을 보관한다. 참여자 이름, 제출 ID, 회원 연결코드, 이메일·전화번호, 카카오 토큰을 합산 내용에 넣지 않는다. 내부 Room 관계를 판매자 응답으로 그대로 직렬화하지 않는다. 6단계에서 카페 권한에 따라 허용 필드만 반환해야 한다.
- 기존 `Room.menu_snapshot`을 바탕으로 원 단위 가격과 옵션 수량을 다시 검증·계산한다. 전송 요청의 메뉴/가격/총액 값은 사용하지 않는다. 수량이 다른 옵션은 별도 행으로 합친다. 기존 옵션 수량 생략은 1개로 처리한다.
- 확인 서명은 주문방 ID, 합산 내용, 접수별 ID·버전의 해시를 묶으며 10분 동안만 유효하다. 별도로 생성 30분 기한을 다시 검사한다. 접수 버전이 바뀌었으면 합계가 같아도 재확인한다.
- 쓰기는 항상 Room을 먼저 잠근다. 최종 전송은 이어 Cafe를 잠그고 영업 상태를 검사한다. 카페 잠금을 기다리는 사이 30분이 지났는지도 재확인한다. 전송·수정·폐기·취소·기한 처리를 직렬화한다.
- PostgreSQL 트리거로 최종 주문서 UPDATE/DELETE, 전송된 접수 INSERT/UPDATE/DELETE, 전송된 수정 이력 변경/추가, 기존 처리 이력 덮어쓰기/삭제, 전송 상태 되돌리기를 차단한다. 취소/거절 이후에도 보호한다. 기존 메뉴판·연락처 사본 불변 트리거도 유지한다.
- 회원 파기에서 감사 기록의 actor와 주문방 회원 관계를 NULL로 끊는 것은 허용하지만 다른 계정으로 재배정하거나 주문 사본을 바꿀 수 없다. 실제 보유·익명화 정책은 파일럿 준비 단계에서 확정한다. DB 소유자가 트리거를 해제하는 등 서버 운영 권한 자체를 제한하는 보장과는 구분한다.
- 상태와 처리 시각/거절 사유의 조합, 전송 기한이 `sent_at + 5분`이라는 점을 DB 제약으로 검사한다. 전송 중 예외가 발생하면 최종 사본·상태·전송 이벤트를 모두 롤백한다. 정상적으로 기한을 처리한 경우에는 예외 대신 결과를 반환해 기한 상태 변경을 커밋한다.
- 마이그레이션은 최종 주문 테이블·처리 필드·제약·트리거를 추가하며 기존 데이터를 재작성하지 않는다. 새 거절 사유 열에는 DB 기본값을 둬 배포 중 이전 웹 프로세스가 새 열을 생략해도 기존 링크 생성을 유지한다.

## 기한 처리

기존 `run_deadlines`를 확장했다. 미전송 30분 폐기와 전송 후 5분 미수락 거절을 5초 간격으로 처리하고 재시작 시 놓친 기한을 처리한다. `skip_locked`와 Room만의 행 잠금, 상태 검사·고유 이벤트 제약으로 중복 처리하지 않는다. 조회는 상태/기한에 맞는 후보만 묶어 처리한다.

Railway의 기존 웹 서비스와 감독 프로세스 구성을 그대로 쓴다. 새 서비스·Redis·외부 스케줄러·카카오 메시지/알림톡·발송 키는 추가하지 않았다. 회원의 기존 카카오 설정과 세션을 유지한다.

## 검증

검증 결과와 실제 배포는 완료 후 아래에 기록한다. 자동 테스트는 별도 PostgreSQL 테스트 DB, 실제 HTTP/기한 검증은 별도의 일회용 DB에서 수행한다. 전송 자료를 지우기 위해 보호 트리거를 끄지 않으며 검수 후 일회용 DB 전체를 제거한다. Railway에는 가짜 검수 주문을 만들지 않는다.

## 다음 범위

6단계에서 판매자의 자기 카페 합산 주문 조회, 수락 시 5분 단위 완료시간 입력, 1~30자 사유를 포함한 거절, 이후 준비·픽업 처리를 구현한다. APNs·FCM 앱 푸시는 후속 앱 단계로 유지한다. 수락 화면이 아직 없으므로 이번 테스트 사이트 전송은 취소하거나 5분 뒤 자동 거절되는 흐름까지 확인한다. 실제 카페 파일럿 주문에 사용하는 단계가 아니다.

### 자동·화면 검사

- 전체 PostgreSQL 테스트 **122개 통과**. 신규 33개는 합산/옵션 수량·개인정보 제외, 확인 서명/버전, 재전송·중단 시 원자성, 영업종료 및 30분 경계 차단, 전송 후 5분 경계, 취소/수락 상태 보호, 실제 워커 명령과 상태 API, DB 직접 수정·삭제 차단을 포함한다.
- 서로 다른 DB 연결에서 동시 전송, 편집/전송, DB 직접 쓰기/전송, 전송/카페 로그아웃, 전송/주문서 삭제, 다중 워커/기한 정각 취소를 경합시켜 하나의 일관된 상태와 이력을 확인했다.
- Chromium 320·390·1440px에서 실제 CSRF 폼으로 마감→합산 확인→전송→잠금→취소를 검증했다. 확인 후 주문 변경의 409와 재확인, 참여자 이름 없는 확인 페이지, 개인정보 안내 위치, 옵션 수량을 반영한 금액, 전송 후 공유 링크 410, 가로 넘침 없음·JavaScript 오류 없음을 확인했다.
- Ruff·형식·JavaScript 구문·마이그레이션 차이 없음·개발 PostgreSQL 마이그레이션 및 쓰기/읽기 검사를 통과했다.

6단계에서 수락 이후 준비/픽업 상태를 추가할 때에는 `Room` 상태·처리 시각 제약과 상태 전이 트리거를 함께 확장해야 한다. 최종 합산 내용과 원본 접수 보호는 유지한다. 현재 `accepted`는 취소·기한 처리 방어를 검증하기 위한 상태이며 사용자 수락 화면은 아직 제공하지 않는다.

### 실제 5분 경과 검증

전송 시각·기한을 단축하거나 수정하지 않고 실제 **300초**를 기다렸다. 서로 분리한 두 주문 중 하나는 페이지나 상태 API를 한 번도 요청하지 않았다. 300초까지 대기였고 이후 정상 워커 주기 안에서 DB가 `rejected`와 `5분 미응답`으로 변했다. 다른 주문은 대기 화면을 열어 두었으며 자동 조회/새로고침으로 같은 거절 상태를 표시하고 취소 버튼을 제거했다. 전송 사본과 시각은 바뀌지 않았고 거절 이벤트는 한 번이었다. 워커를 중지한 뒤 `--once`로 재시작해 이력이 중복되지 않음을 확인했다. 검수용 DB 전체를 제거했으며 일반 개발·Railway 데이터는 변경하지 않았다.

## 배포 제한 이력 — 해제 후 배포 완료

Railway CLI 배포를 두 차례 시도했으나 모두 `UPLOAD_FAILED: Deploys have been paused temporarily`로 거절되어 새 배포 ID가 만들어지지 않았다. 토큰 인증과 프로젝트 조회는 정상이다. 플랫폼 상태 API는 stable/incident 없음으로 응답해 중지의 상세 원인을 특정하지 못했다. 요금제 변경·토큰 재발급·다른 서비스 생성이나 제한 우회는 수행하지 않았다. 사용자에게 대시보드의 추가 중지 문구를 요청했다.

배포 제한 당시 공개 주소의 홈·DB 준비·생존 응답은 모두 200이며 마지막 성공 배포는 `065044d8-ff16-4812-8ffd-3d0dd89a7925`였다. 그 시점에는 5단계가 공개 반영되지 않았다. 기존 데이터와 서비스는 유지했다. 기존 `preDeployCommand`는 `.venv/bin/python manage.py migrate --noinput`만 포함한다.

### 2026-10-21 재개 결과

사용자가 배포 재개를 요청해 같은 프로젝트/환경/웹 서비스에 재시도했고 배포 `c40688bf-cca2-47c4-9ce0-f1ba27446dbf`가 `SUCCESS`로 완료됐다. **5단계가 공개 테스트 사이트에 반영됐다.** 실제 Railway 로그에서 마이그레이션 0004/0005 정상 적용과 Gunicorn·기한 처리 프로세스 시작을 확인했다.

공개 HTTPS에서 홈·PostgreSQL 준비·생존 응답 200, 주문/관리 정적 CSS/JS 5개와 소스 일치를 확인했다. 새 최종 확인/상태 API는 비로그인 시 로그인 입구로 이동하고 no-store이며, 전송/취소는 GET 405·CSRF 없는 POST 403이다. 기존 편집 경로의 로그인 보호와 존재하지 않는 공유 링크의 404도 유지한다. CSRF 폼을 통한 카카오 인증 시작 302·정확한 콜백·닉네임만 요청·OAuth 상태를 확인했고 실제 계정 인증을 대신하지 않았다. 원격 검증은 실제 주문이나 가짜 회원을 생성하지 않았다. 실제 300초 경과 검증은 위의 분리된 검수 DB 기록과 구분한다.

사용자 확인 범위는 마감→전송→수정 차단→수락 전 취소 또는 5분 자동 거절이다. 판매자 수락·거절 화면과 완료시간 입력은 6단계로 남기며 이번 배포에 포함하지 않았다.

## 총무 주문서 간소화 보완

사용자 요청으로 참여자별 큰 카드·접수 시각·개인별 소계를 제거하고 네 열의 표로 바꿨다. 옵션은 메뉴 셀 안에서 작게 이어 표시하고 길면 셀 내부에서 줄바꿈한다. 수정은 해당 참여자의 전체 주문 편집으로 연결하며, 참여자 주문 삭제는 그 편집 화면으로 옮겼다. 삭제도 편집 화면에서 보던 버전으로 검사하므로 다른 창에서 바뀐 주문을 지우지 않는다. 전송 후·읽기 전용 조회에서는 수정 열을 표시하지 않는다.

마감 후 주문서 자체에 서명된 전송 폼과 개인정보 안내를 표시한다. 표시한 접수와 전송 서명은 같은 Room 잠금 안에서 읽어 일치시키며, 기존 10분 서명·30분 폐기·중복 전송 방지·최종 내용 고정·5분 자동 거절을 유지한다. 이전 `/confirm/` 주소는 권한 검사 후 주문서로 돌려보내고 기존 별도 확인 템플릿은 제거했다.
