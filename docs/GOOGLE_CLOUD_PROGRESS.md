1. 새 암호를 자동 생성해 서울 지역 Secret Manager의 `yeongcha-database-url`

2. 해당 암호로 DB 사용자 `yeongcha_app`을 만든다. 기존 사용자 암호를 재설정하지 않는다.
3. 해당 비밀값 하나에만 웹 실행 계정의 `secretAccessor`를 부여한다.

비밀값을 먼저 저장하므로 사용자 생성이 중단돼도 다음 실행에서 같은 암호를
재사용한다. 기존 사용자가 있는데 비밀값이 없거나, 저장된 값이 다른 DB를
가리키거나, 상태/권한 조회에 실패하면 임의 수정하지 않고 중단한다.
Secret Manager 버전 1이 제거/비활성화된 경우도 실패를 숨겨 새 암호를 만들지 않는다.

5. Google이 반환한 실제 HTTPS 주소의 호스트를 Django 허용 호스트에 등록한다.
   이후 테스트 서비스의 공개 접근을 설정한다. 허용 호스트 `*`는 사용하지 않는다.
6. 공개 HTTPS의 홈, 프로세스 생존, 실제 DB 준비 응답을 확인한 후 테스트 URL을

## 사용자 결정 — 원본 테스트 데이터 이전 생략

사용자는 기존 데이터가 모두 테스트용이므로 보존할 필요가 없고 다시 입력하겠다고
답했다. 원본 DB 백업·복원과 기존 Django 비밀키 전달을 생략한다. Railway API
접근 거부는 이제 이 작업의 차단 요인이 아니다. 기존 데이터를 지우거나 Railway를
종료한 것은 아니며 원본 데이터 이전을 성공했다고 보고하지 않는다.

Google에 생성한 DB와 별도 서명 키를 사용한다. 카카오 앱은 기존 영차 앱을
재사용한다. 신규 Google 계정의 연결 코드와 운영자·판매자 권한은 다시 확인한다.
이전 Railway 연결 코드 `ec796276-bd4e-461c-bca3-c9a01fcec831`는 Google의
현재 계정 코드로 가정하지 않는다. 첫 가입자를 자동 운영자로 지정하지 않는다.
카페·메뉴·옵션은 사용자가 새로 등록한다.

다음 사용자 작업은 기존 카카오 앱의 로그인용 REST API 키 상세에 다음 로그인
Redirect URI를 추가하는 것이다. Secret 값을 채팅으로 요청하지 않는다.

`https://yeongcha-test-t7e4i53n5q-du.a.run.app/accounts/kakao/login/callback/`

등록 후 카카오 REST API 키와 카카오 로그인용 Client Secret을 Secret Manager에
안전하게 저장하고 런타임 계정에 해당 비밀값 접근만 허용한다. 서버 변수 이름은
사용자 결정인 `KAKAO_RESET_API_KEY`를 유지하고 값은 실제 REST API 키를 사용한다.
Secret 연결이 준비된 뒤 `KAKAO_LOGIN_ENABLED=True`로 바꾼다. 이 파일 기록 시점에는
Redirect URI 등록·키 전달·실제 왕복 로그인·신규 운영자 연결은 아직 확인 전이다.

## 새 Redirect URI 등록 확인과 키 연결 준비

사용자가 기존 카카오 앱에 Google 주소의 로그인 Redirect URI를 등록했다고 확인했다.
`scripts/gcp_configure_kakao.py`를 준비했다. 다음 동작은 사용자 Cloud Shell에서만
수행하며 에이전트에게 키 값을 전달하지 않는다.

- 입력 1: REST API 키 상세 상단의 실제 32자리 REST API 키 값. 관리용 이름이 아니다.
- 입력 2: 같은 앱의 카카오 **로그인용** Client Secret. 비즈니스 인증용이 아니다.
- 터미널 입력을 숨길 수 없으면 입력받지 않고 중단한다. 키를 일반 셸 명령에
  붙여넣지 않으며 입력 안내가 표시된 Python 프로세스 안에서만 입력한다.
  모바일 재접속으로 `$` 프롬프트로 돌아온 경우 값을 붙여넣지 말고 다시 실행한다.
- 각각 서울 Secret Manager의 `yeongcha-kakao-rest-api-key`,
  `yeongcha-kakao-login-secret`에 저장한다. 웹 실행 계정은 이 두 비밀값에만
  추가 접근 권한을 받는다. 키를 화면·Git·로컬 파일·셸 이력에 쓰지 않는다.
- 저장된 비밀값이 있으면 활성 버전을 재사용한다. 명시적인 `--replace-keys`
  옵션으로만 새 입력을 받아 버전을 추가한다. 배포에는 숫자 버전을 고정한다.
- 두 키 준비 후에만 `--update-secrets`와 `--update-env-vars`로 카카오 관련
  설정을 병합한다. DB URL·Django 키·허용 호스트·상시 CPU 설정을 덮어쓰지 않는다.
- `yeongcha-kakao=enabled` 라벨을 붙인다. 초기 테스트 배포 스크립트는 이
  라벨이 있는 서비스에서 실행을 거부해 로그인 설정을 되돌리지 않도록 했다.
- 실제 공개 HTTPS·DB 준비와 CSRF 보호된 로그인 시작 요청을 검사한다.
  카카오 서버를 따라가지 않고 이동 주소의 공급자·콜백·인증 코드 방식·state·
  닉네임 단일 scope를 검사한다. 실제 카카오 비밀번호/동의·콜백 완료를 대신하지 않는다.

검증: 기존 안전성 검사와 새 설정/재실행/키 교체/무노출/잘못된 값 거부/
CSRF 쿠키·HTTP 이동 응답 검사를 합해 로컬 테스트 24개 통과. 로컬 HTTP 검사 시
외부 HTTPS 접속을 차단하는 테스트 핸들러를 사용했다. 실행 환경의 로컬 소켓 제한
때문에 해당 검사를 허용된 테스트 실행 권한으로 재실행해 성공했다.
Google의 실제 키 연결과 로그인 결과는 아직 사용자 실행 전이다.

## 카카오 연결 실행 성공과 신규 운영자 지정 준비

사용자가 Cloud Shell에서 두 키 저장과 웹 연결, 사이트·DB·카카오 로그인 시작
검사까지 성공한 출력을 전달했다. 이후 Google 사이트에서 본인 계정 연결 코드를
전달했다. 이전 Railway 코드가 아닌 새 Google 계정 코드를 사용한다. 새 코드 자체는
이 문서에 공개하지 않고 운영 설정에만 사용한다.

운영자 지정은 이미 구현된 `INITIAL_OPERATOR_ACCOUNT_CODE` 방식을 사용한다.
Cloud Run의 `--update-env-vars`로 전달받은 정확한 코드만 임시 지정한다.
다른 환경변수나 카카오/DB Secret 연결은 유지한다. 사용자가 로그아웃 후
카카오로 다시 로그인하면 기존 `select_initial_operator`가 다음을 검사한다.

- 로그인 계정의 연결 코드가 지정 코드와 일치함.
- 활성 회원이고 실제 카카오 연결이 있음.
- 아직 운영자가 없는 초기 환경임.

일치한 본인 계정에만 권한을 부여한다. 첫 방문자나 첫 가입자를 자동 운영자로
지정하지 않는다. 운영자 페이지 접근 확인 후 임시 변수는 제거하며 DB에 저장된
권한은 유지된다. 이후 카페를 새로 등록하고 본인 계정을 판매자로 연결한다.

현재 상태: 운영자 지정 명령은 사용자에게 안내할 준비가 됐고, Google 적용과
재로그인·운영자 페이지 확인은 아직 실행 결과를 받지 않았다. 새 관리 작업이나
DB 직접 수정 대신 기존에 검증된 최초 운영자 연결 기능을 사용한다.
