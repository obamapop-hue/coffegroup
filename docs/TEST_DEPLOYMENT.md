# Railway 테스트 배포 기록

최신 진행: 6단계 판매자 처리 구현·153개 테스트·실제 5분 경과 검증을 마쳤으나 Railway 공식 빌드 중단 장애로 새 배포가 차단됐다. 아래 현재 성공 배포는 5단계이며 [6단계 상태](PHASE_6.md)를 참고한다.

기록일: 2026-10-20. 사용자 요청으로 1단계 테스트 사이트를 배포했고 이후 승인을 받아 2단계 계정·권한을 구현했다. 카카오 로그인 성공과 본인 운영자·판매자 권한 연결을 확인했다. 주문 기능·파일럿 공개는 후속 단계다.

## 현재 상태

- **외부 테스트 배포 완료:** https://coffegroup-web-production.up.railway.app
- 사용자가 공급한 프로젝트 토큰과 네트워크 허용의 실제 반영을 확인했고 해당 프로젝트 API 인증에 성공했다. 토큰 값은 출력·소스 저장하지 않았다.
- 프로젝트: `2ba98b24-c561-4385-8f7e-12523f21ecfc` / 환경: `5cc573ae-94a6-437c-aef0-0d2dd2c0f56f` (`production`은 Railway 기본 환경 이름이며 서비스 전체 공개 출시를 뜻하지 않는다).
- 웹 서비스: `bb90c86f-6395-4760-b8f9-db2cbb940cc2` (`coffegroup-web`).
- DB 서비스: `f5c1dc54-bcc1-4f3e-8db1-3560e2dfad00` (`Postgres`).
- 현재 성공한 웹 배포: `94a3e8c3-584c-4d7a-b90b-8b7dbe2a5fd1`, Railway 상태 `SUCCESS` 확인.
- 실제 HTTPS에서 기본 화면·CSS·웹 생존 확인·PostgreSQL 준비 상태 모두 HTTP 200을 확인했다.
- 현재 5단계 최종 확인·전송·내용 잠금·수락 전 취소·5분 자동 거절까지 테스트 배포했다. 판매자 주문 처리 화면·알림은 다음 단계다.

## 3단계 메뉴·주문방과 개인정보

- 후속 배포 `3b1a9ab6-9021-476d-87f4-d1199413a65b` 성공. 개인정보의 연결코드 옆에 겹친 네모 SVG 복사 버튼을 추가했다. Chromium 320·390·1440px에서 실제 클립보드에 본인 코드가 정확히 복사되는지, 대체 복사와 실패 안내, 가로 넘침을 확인했다. 계정·권한 관련 테스트 14개와 Ruff 검사가 통과했다.
- 사용자가 직접 확인해 전달한 연결코드에 한정해 서버 관리 명령으로 운영자·판매자 권한을 연결했다. `영차 테스트 카페` 연결과 성공 로그를 확인했으며 실행 중인 배포가 SUCCESS임을 확인했다. 일회성 배포 전 명령은 기존 마이그레이션 명령으로 복구했다. 계정 코드 자체를 소스나 문서에 저장하지 않았다. 실계정 브라우저에서 판매자 페이지 클릭 검수는 사용자 확인 대기다.
- 실제 HTTPS에서 홈·DB 준비·카카오 인증 시작, 공개 복사 스크립트가 소스와 일치하는지 확인했다.

- 배포 `648069c2-1fb5-475b-8ce3-7a72e5bf3927` 상태 `SUCCESS`. 실제 Railway에서 웹과 기한 처리 프로세스 시작 로그를 확인했고 DB 연결 오류는 없었다. HTTPS 홈·실제 DB 준비 200, 카카오 인증 시작 302, 개인정보·관리 화면의 로그인 제한, 주문방 생성 GET 405, 존재하지 않는 참여 주소의 DB 조회 후 404, 개인정보·이력 CSS 반영을 확인했다.
- 개인정보 페이지 초판 배포 `86af5295-df97-4c84-ab94-039b089fa9b7` 이후 메뉴·옵션·연락처·고정 메뉴판·실제 주문방 이력·30분 폐기 처리를 추가했다. 검증은 [3단계 기록](PHASE_3.md)에 정리했다. 권한 검증용 임시 데이터는 로컬에만 사용하고 제거했다.
- 사용자가 본인의 연결코드를 알려주면 운영자·판매자 연결을 마친다. 아직 실계정 권한 연결 완료로 보고하지 않는다. 새 코드나 키를 추측해 적용하지 않았다.

## 2단계 계정·권한 테스트 배포

- 화면 정리 배포 `585f5497-14e3-4054-9e3a-d8dd34702c91` 성공. HTTPS에서 새 기본 로그인 입구 문구·역할 표시 제거·갱신된 하단 CSS와 홈·DB 준비 200·카카오 인증 시작 302를 확인했다. 실제 로그인 화면은 사용자 세션을 대신 사용하지 않고 로컬 권한별 검수로 확인했다.

- 사용자가 실제 카카오 로그인 성공을 확인했다. 이후 기본 주문 화면 중심으로 상단 역할 표시·전환 메뉴를 제거하고 권한에 따른 하단 이동 버튼으로 변경했다. 실제 PostgreSQL 테스트 31개 통과, 320px·390px·1440px에서 화면과 판매자 이동·로그아웃을 확인했다. 운영자·판매자 실계정 연결 검수는 남아 있다.

- 사용자가 Railway 변수 이름을 변경한 뒤 배포 `07da39fc-d875-438a-ba69-179483a5cd54` 성공을 확인했다. 현재 `KAKAO_RESET_API_KEY`가 있고 기존 `KAKAO_REST_API_KEY`는 없다. 값은 출력하지 않았다. 공개 사이트 홈·DB 준비 200, 카카오 인증 시작 302·콜백·닉네임 scope·상태 확인 통과. 사용자 실제 카카오 로그인은 검수 대기다.

- 배포 `92abddab-b85a-4c50-81ee-1332e14b829f` 성공. 실제 HTTPS 홈·DB 준비 200 및 CSRF가 적용된 카카오 인증 시작 302·콜백·닉네임 scope·상태를 확인했다. 실제 카카오 계정 로그인은 사용자 검수 대기다.
- 후속 사용자 요청으로 기본 변수 이름을 `KAKAO_RESET_API_KEY`로 변경했다. Railway에서 이름 변경은 사용자가 진행하며 기존 값을 유지한다. 서버는 변경 중에도 동작하도록 기존 `KAKAO_REST_API_KEY`를 대체 이름으로 지원한다. `RESET` 단독·기존 `REST` 단독·두 이름 동시 설정 시 `RESET` 우선 적용을 확인했고 기존 29개 테스트가 통과했다.
- 사용자 카카오 설정 후 배포 `bf3cfeea-45eb-4ebf-a020-7db3c571f9de`가 설정 검사에서 실패했다. 변수 이름만 확인한 결과 `KAKAO_RESET_API_KEY`로 등록되어 있었고 서버가 요구하는 `KAKAO_REST_API_KEY`는 없었다. 기존 값을 출력하지 않고 올바른 이름에 그대로 옮겨 검증한 뒤 잘못된 이름을 삭제했다.
- 수정 후 배포 `dafe679b-ce4d-492b-8e0c-26818b19c380` 성공. 실제 HTTPS에서 로그인 버튼 활성, CSRF가 적용된 로그인 시작 POST의 카카오 인증 URL 302, 정확한 콜백 주소·닉네임 전용 scope·OAuth 상태 포함, DB 준비 200을 확인했다. 카카오 쪽으로 리다이렉트를 따라가거나 사용자 계정 인증을 대신하지 않았다. 본인의 실제 로그인과 운영자·판매자 연결은 다음 검수다.

- django-allauth 카카오 로그인, 역할별 화면과 서버 권한, 최초 운영자 지정, 카페·판매자 연결, 판매자 로그인·로그아웃의 영업 상태를 추가했다. DB 마이그레이션은 기존 서비스의 pre-deploy 명령으로 적용한다.
- 실제 카카오 키가 없는 상태에서는 버튼 비활성 및 직접 인증 요청 차단을 유지한다. 가짜 로그인·테스트용 권한 우회 URL은 배포하지 않는다.
- [카카오 연결 가이드](KAKAO_SETUP.md), [2단계 구현·검증 기록](PHASE_2.md)을 함께 준비했다. 실계정 연결은 설정 후 별도로 검수하며 완료라고 미리 보고하지 않는다.
- Railway 최종 배포 `SUCCESS`. 실제 HTTPS에서 세 로그인 입구 200, 비로그인 보호 화면은 해당 입구로 302 이동, GET 로그아웃 405, CSRF 없는 POST 로그아웃 403, 비밀번호 가입 경로 404를 확인했다. 카카오 미설정 상태의 인증 시작·콜백은 503으로 차단됐다. CSS와 DB 준비 경로는 200이며 쿠키 Secure 설정도 확인했다.
- 최초 배포 `33960042-fab1-4039-99ae-d8906d8cb532` 이후, 초기 운영자 지정 절차와 Docker 소유권 변경 최적화를 포함한 최종 버전을 배포했다. 로컬 화면 검수용 임시 회원을 Railway에 만들지 않았다.

## 승인한 윤곽선 로고 적용과 공유 이미지

- 사용자가 검토한 윤곽선 팔 일러스트의 적용을 승인했다. 원본 그림의 투명 여백을 정리하고 비율을 유지해 사이트용 192px PNG와 파비콘 64px PNG를 내보냈다. 그림 자체를 다시 그리지 않았다.
- 공유용은 1200×630 흰 배경에 약 470px 크기의 팔을 가운데 배치했다. 중앙 정사각형으로 잘려도 그림이 남는 여백을 확보했다. 파일은 약 62KB다.
- 기본 화면에 Open Graph와 Twitter 카드 메타를 추가했다. 공유 제목은 기존 사이트 제목, 설명은 승인된 메인 문구를 사용한다. 이미지와 사이트 URL은 검증된 요청 호스트에서 절대 주소로 생성하며 이미지 URL에는 운영 정적 파일 해시가 반영된다.
- 로컬 Chromium 320px·390px·1440px에서 새 로고, 공유 이미지와 메타, 첫 화면 시작 버튼을 확인했다. 공유 PNG의 크기·흰 배경·중앙 크롭 여백을 확인했다. 기존 화면 테스트 3개와 변경한 Python 파일의 Ruff 검사를 통과했다.
- Railway 배포 `SUCCESS`를 확인했다. 실제 HTTPS에서 새 로고·파비콘·1200×630 공유 PNG가 로컬 산출물과 일치하고, 공유 이미지가 해시된 절대 HTTPS 주소이며 메타·이미지가 비로그인 크롤러 요청으로 200 응답함을 확인했다. DB 준비 경로도 200이다.
- 카카오톡 실제 앱의 공유 카드 렌더링은 직접 검증하지 않았다. 기존 URL의 공유 미리보기는 카카오톡 캐시에 의해 이전 상태가 남을 수 있으며 이미 보낸 메시지 카드까지 소급 변경되는 것은 아니다.

## 새 윤곽선 팔 일러스트 검토

- 사용자는 새 팔 일러스트를 먼저 검토하고 사이트 로고에는 아직 적용하지 말라고 요청했다. 채팅에서 생성 이미지가 보이지 않아 별도 정적 미리보기 주소를 추가했다.
- 검토 페이지: `/static/previews/yeongcha-arm-outline.html`. 원본 PNG: `/static/previews/yeongcha-arm-outline.png`.
- 생성한 투명 PNG를 그대로 복사했고, 검토 페이지에서 흰 배경으로 보여 준다. 메인 템플릿의 로고 참조와 기존 로고 PNG·파비콘은 교체하지 않았다.
- 로컬 Chromium 모바일 크기에서 미리보기 이미지 로딩·흰 배경·가로 넘침 없음을 확인했다.
- 배포 `SUCCESS` 및 실제 HTTPS의 미리보기 HTML·PNG·DB 준비 경로 200을 확인했다. 공개 PNG가 원본과 바이트 단위로 일치하고 메인 화면 HTML은 배포 전과 동일함을 확인했다.

- 메인 설명은 `한 명씩 묻고, 따로 적을 필요 없이. / 각자 고른 커피가 하나의 주문서로 모여요.`로 바꿨다.
- 로컬 Chromium의 320px·390px·1440px에서 승인 문구·사용법 가로 배치·텍스트 넘침 없음·모바일 첫 화면의 시작 버튼을 확인했다. 기존 화면 테스트 3개가 통과했다.
- Railway 배포 `SUCCESS`와 실제 HTTPS의 승인 문구 4개·기존 고정 버튼 CSS·상태 경로 200을 확인했다.

## 모바일 사용법 가로 배치와 시작 버튼

- 600px 이하에서도 사용법 1~3단계를 동일한 행의 3열로 표시한다. 제목 20px·설명 14px와 기존 문구를 유지하고 열 사이 여백과 줄바꿈을 조정했다.
- 모바일의 시작 버튼·기존 준비 중 안내를 흰색 하단 바에 고정했다. 작은 화면에서도 스크롤 없이 버튼 전체가 보인다. 본문 하단에는 바 높이와 휴대폰 안전 영역을 고려한 여백을 두어 마지막 판매자·운영자 메뉴까지 스크롤해 볼 수 있다.
- PC에서는 기존 위치에 버튼을 표시한다. 로그인 기능을 새로 구현하거나 비활성 상태를 해제하지 않았다.
- 로컬 Chromium에서 320×480부터 600×800까지 모바일 8개 크기와 태블릿·PC 2개 크기를 확인했다. 사용법 가로 배치, 텍스트·페이지 가로 넘침 없음, 첫 화면 버튼 노출, 스크롤 후 버튼 위치 유지, 하단 메뉴 노출을 확인했다. 기존 화면 테스트 3개도 통과했다.
- Railway 배포 `SUCCESS`와 실제 HTTPS의 새 시작 버튼 영역·모바일 3열 및 고정 바 CSS·상태 경로 200을 확인했다.

## 휴대폰 다크 모드에서 흰 배경 유지

- 사용자는 GPT Codex 안에서 링크를 열었을 때 배경이 검게 표시된다고 보고했다. 기존 CSS의 `color-scheme: light`만으로는 브라우저의 자동 다크 변환을 막지 못했다.
- 페이지 메타에 `color-scheme: only light`와 구형 브라우저용 `supported-color-schemes: light`를 추가했다. CSS도 `only light`로 변경하고 본문 배경·글자색을 명시했다.
- 로컬 Chromium의 자동 다크 변환을 CDP로 켜 기존 화면의 실제 배경 픽셀이 `(18,18,18)`로 바뀌는 것을 재현했다. 수정 후 390px·1440px의 일반/다크/자동 다크 조합 6개에서 실제 스크린샷 배경이 모두 `(255,255,255)`임을 확인했다. 기존 화면 테스트 3개도 통과했다.
- 이 검증은 Chromium의 자동 변환 검증이며 사용자의 실제 Codex 내장 브라우저나 OS 전체 색상 반전 설정을 직접 검증한 것은 아니다.
- 같은 Railway 서비스의 배포 `SUCCESS` 확인 후 실제 HTTPS에서 새 메타·해시된 CSS의 `only light`와 본문 배경 명시·상태 경로 200을 확인했다.

## 준비한 파일과 동작

- `Dockerfile`: 고정된 Python 이미지·잠금파일 기반 설치, 비특권 사용자 실행. Railway의 정상 시스템 TLS 신뢰로 설치하며 로컬 프록시 CA를 이미지에 넣지 않는다.
- `.dockerignore`, `.railwayignore`: `.env`, 가상환경·캐시·로그를 업로드·이미지에서 제외한다.
- `scripts/start_web.sh`: 정적 파일 수집 후 Gunicorn으로 실행. Railway의 `PORT`를 읽는다. Django 개발 서버를 공개하지 않는다.
- `config/settings.py`: 운영 모드 WhiteNoise 정적 파일·HTTPS 프록시·호스트 제한. 플랫폼의 `RAILWAY_PUBLIC_DOMAIN`과 Railway 상태 확인 호스트를 허용한다.
- `pyproject.toml`, `uv.lock`: Gunicorn·WhiteNoise 의존성을 추가·고정했다.

공식 문서의 현재 버전은 기존 `railway.toml`/`railway.json` 방식의 신규 사용을 권하지 않으므로 이 작업에서는 새 레거시 설정 파일을 만들지 않았다. Dockerfile 자동 감지와 아래 서비스 설정을 사용한다.

## 최초 계정 연결 절차 — 현재 완료

1. Railway 공식 사이트에서 본인 계정을 만든다. 약관 동의·계정 소유·플랜 선택은 사용자가 직접 한다. 유료 플랜 결제를 임의로 진행하지 않는다.
2. 빈 테스트 프로젝트를 하나 만든다. GitHub에서 자동 배포를 연결할 필요는 없다. 현재 소스는 작업공간에 있으며 원격 저장소에 올렸다고 가정하지 않는다.
3. 프로젝트 설정의 Tokens에서 해당 프로젝트 환경에 한정된 토큰을 발급한다. 계정 전체 토큰은 요구하지 않는다.
4. 이 작업의 개발 환경 설정에서 준비된 `RAILWAY_TOKEN` 비밀값 항목에 안전하게 입력한다. 토큰을 채팅에 붙여 넣거나 저장소에 기록하지 않는다. 네트워크 변경도 함께 검토·저장하고 개발 환경을 게시(Publish)해 반영한다. 이는 웹사이트 배포와 별개다.
5. Railway 프로젝트의 일반 대시보드 URL만 채팅에 알려 준다. 인증 토큰이 포함된 URL은 보내지 않는다.

이 절차의 완료 후 API 인증을 직접 재확인하고 같은 프로젝트에 DB·웹 서비스를 생성했다. 로컬 작업공간의 소스를 CLI로 업로드했다. GitHub 원격 push나 GitHub 자동 배포 연결은 수행하지 않았다. 토큰을 재발급할 때도 실제 API 접근을 재확인한다.

## 배포할 서비스 설정

하나의 테스트 프로젝트에 PostgreSQL과 웹 서비스를 둔다. 기존 개발 환경의 비밀값이나 DB 데이터를 업로드하지 않고 테스트 서비스 전용 값을 사용한다.

| 설정 | 값·원칙 |
| --- | --- |
| Builder | 저장소 루트 Dockerfile 자동 감지 |
| Start command | Dockerfile의 기본 CMD: `bash scripts/start_web.sh` |
| Pre-deploy command | `.venv/bin/python manage.py migrate --noinput` |
| Healthcheck | `/health/ready/` — PostgreSQL 쿼리 성공 필요 |
| Public networking | Railway 제공 도메인을 생성하고 플랫폼 `PORT`로 연결 |
| Debug | `DJANGO_DEBUG=False` |
| Proxy | `DJANGO_TRUST_PROXY=True` — Railway가 제공하는 HTTPS 헤더 신뢰 |
| Hosts | `DJANGO_ALLOWED_HOSTS=healthcheck.railway.app`, 실제 공개 도메인은 `RAILWAY_PUBLIC_DOMAIN`으로 추가 |
| Secret key | 테스트 서비스 전용 무작위 값을 생성해 Railway 변수로 저장. 출력·소스 저장 금지 |
| Database | 같은 프로젝트 PostgreSQL의 비공개 `DATABASE_URL` 참조 |

웹 서비스는 DB가 준비되고 마이그레이션이 끝난 후 활성화한다. `DATABASE_URL`에 SQLite나 가짜 DB를 지정해 준비 상태를 통과시키지 않는다. 도메인 생성 후 공개 도메인 변수 반영 여부를 확인하고 필요하면 재배포한다.

## 검증 결과

- 실제 Docker 빌드 성공. 런타임은 UID 10001이며 `.env`와 빌드 CA 번들이 이미지에 없음을 확인했다.
- `DJANGO_DEBUG=False`로 Gunicorn 실행, 정적 파일 수집·해시된 CSS 응답 200.
- 실제 PostgreSQL 연결로 `/health/ready/` 응답 200.
- Railway 상태 확인 호스트 및 플랫폼 공개 호스트 설정을 로컬에서 모사해 200 확인.
- 일반 HTTP 요청은 HTTPS로 301 전환. Railway HTTPS 종료를 모사한 헤더로 기본 화면 200.
- 허용하지 않은 Host는 400, 존재하지 않는 경로는 디버그 상세 없는 404.
- 기존 Django 자동 테스트 5개 통과, 마이그레이션 차이 없음, Ruff 검사 통과.

이 결과는 로컬 배포용 이미지 검증이다. 실제 외부 HTTPS 연결·인증서·Railway 배포 성공을 의미하지 않는다. 배포 완료 보고에는 실제 주소와 해당 주소의 기본 화면·CSS·DB 준비 상태 검증 결과를 포함해야 한다.

외부 배포 후 별도로 확인한 결과:

- Railway 웹 배포 상태 `SUCCESS`.
- 실제 테스트 주소의 기본 화면 HTTP 200, 한국어 제목과 준비 중 문구 확인.
- 해시된 CSS 경로 HTTP 200 및 `text/css` 확인.
- `/health/live/` HTTP 200.
- `/health/ready/` HTTP 200 및 실제 DB 쿼리 결과 `ready` 확인.
- 전처리 명령의 초기 DB 마이그레이션이 모두 적용된 로그 확인.
- 공개 주소의 Playwright 재검증은 이 환경의 Chromium 인증서 신뢰에서 `ERR_CERT_AUTHORITY_INVALID`로 중단됐다. HTTPS 프록시를 통과하는 Python 시스템 신뢰에서는 TLS 검증을 유지한 채 HTTP 200을 확인했다. 브라우저에서 인증서 검증을 끄지는 않았다. 공개 주소의 PC·모바일 브라우저 검수까지 통과했다고 보고하지 않는다. 기존 로컬 PC·모바일 크기 검증과 구분한다.

## 배포 과정에서 해결한 문제와 주의사항

- CLI `link`는 계정 범위 작업을 요구해 프로젝트 토큰으로 실패했다. 토큰이 잘못된 것이 아니며 `status`와 명시적 프로젝트/환경/서비스 지정으로 정상 배포했다. 불필요하게 계정 전체 토큰으로 범위를 넓히지 않았다.
- npm CLI 설치기의 직접 네트워크 요청이 환경 프록시를 사용하지 못했다. 공식 GitHub 릴리스의 동일 버전 CLI를 기존 HTTPS 프록시와 TLS 검증을 유지해 설치했다.
- 첫 웹 배포 `fd4e9209-eb17-4685-8948-01684e44c6d5`는 Railway Metal 빌더가 Dockerfile의 secret mount를 지원하지 않아 실패했다. 로컬 전용 마운트를 제거하고 정상 TLS 다운로드를 사용하는 Dockerfile로 재배포해 해결했다. TLS·패키지 검증을 끄지 않았다.
- Railway 공식 Postgres 템플릿은 이번 배포에서 PostgreSQL 18을 생성했다. 로컬 개발 DB는 기존 PostgreSQL 17이며 기존 볼륨을 삭제하거나 하위 버전으로 바꾸지 않았다. Railway 18에서 초기 마이그레이션·실제 쿼리 성공을 확인했다. 파일럿 전 버전 일치와 복구 정책을 별도로 정리한다.
- 현재 웹·DB는 각 1개 인스턴스이며 기본 제한은 각각 메모리 1GB·CPU 2개다. 고가용성 복제나 유료 플랜 변경은 하지 않았다. 운영 비용은 실제 리소스 사용량에 따라 발생하며 주문 건수만으로 정해지지 않는다.

## 이후 같은 웹 서비스에 다시 배포하기

`RAILWAY_TOKEN` 비밀값이 안전하게 주입된 환경에서 다음처럼 기존 서비스 ID를 지정한다. 토큰을 명령 인자나 소스에 직접 적지 않는다.

```bash
railway up --project 2ba98b24-c561-4385-8f7e-12523f21ecfc \
  --environment 5cc573ae-94a6-437c-aef0-0d2dd2c0f56f \
  --service bb90c86f-6395-4760-b8f9-db2cbb940cc2 --detach --json
```

`--detach` 성공은 업로드·빌드 대기열 등록만 뜻한다. 생성된 배포 ID의 최종 상태와 실제 HTTPS·CSS·DB 준비 상태까지 확인한다. 기존 DB·웹·도메인을 중복 생성하지 않는다.

## 중복 홈 이동 버튼 제거

사용자 요청으로 계정 로그인·권한 안내·로그인 준비·이용 중지 화면의 `메인으로 돌아가기` 링크를 제거했다. 브랜드 로고의 홈 링크는 유지한다. 기존 화면·권한 테스트 17개와 템플릿 응답 확인을 통과했다. 배포 `554921e4-4a6e-4f67-895f-c70ac9d92b2c`가 성공했고 실제 HTTPS의 세 로그인 입구·권한 안내 및 DB 준비 응답을 확인했다.

## 운영자 표 관리 개편

배포 `3f9808e1-4527-4f41-a3a3-f183d9ad673a` 성공. 카페·판매자, 메뉴·옵션을 셀 편집과 여러 행 붙여넣기·일괄 저장 방식으로 개편했다. 기존 데이터는 그대로 두고 저장 이력 테이블만 추가했다. 실제 Railway 로그에서 마이그레이션 정상 적용과 기한 처리 시작을 확인했고 오류 로그가 없었다. 실제 HTTPS에서 새 관리 API의 비로그인 접근 차단, 새 JS/CSS와 소스 일치, 기본 화면·DB 준비 200·카카오 인증 시작 302를 확인했다. 사용자 세션을 대신 사용하거나 가짜 검수 데이터를 Railway에 만들지 않았다. 실제 100개 메뉴 붙여넣기와 모바일·PC 검증, PostgreSQL 테스트 65개는 [검증 기록](ADMIN_SHEETS.md)을 참고한다.

## 옵션 행 표시 수정

배포 `e28389e0-8765-40fc-b561-e2f663e108c8` 성공. 표 높이 제한을 제거해 추가 행이 페이지 아래로 계속 표시되도록 수정했다. 옵션 탭은 전체 옵션을 표시하고 메뉴 행의 옵션 버튼은 다른 행을 숨기지 않은 채 해당 위치로 이동한다. 직접 설정한 필터는 행 수에 명시하고 전체 보기로 해제한다.
