# 4단계 — 주문 제출과 취합

사용자가 4단계 범위인 비회원 주문 제출과 총무의 주문 관리·마감을 승인했다. 최종 전송·판매자 수락/거절·5분 자동 거절·웹 알림은 다음 단계에 남긴다.

## 이용 흐름

1. 총무가 카페를 선택해 주문방 링크를 만든다. 기존 주문방 생성과 고정 메뉴판·30분 폐기 규칙은 유지한다.
2. 비회원은 링크에서 이름(닉네임)을 입력하고 메뉴를 담는다. 아이스/핫·샷 추가 등 해당 메뉴의 기본 옵션이 선택되어 있다. 옵션·수량을 바꿀 수 있고, 같은 메뉴를 다른 옵션으로 여러 번 담거나 여러 메뉴를 한 번에 제출할 수 있다.
3. 제출 완료 화면에는 다른 주문이나 참여자 정보를 표시하지 않는다. 새로고침해도 다시 제출되지 않는다. 참여자에게 수정 화면은 제공하지 않는다.
4. 총무는 주문서에서 참여자별 메뉴·선택 옵션·수량·금액, 총 수량·총액을 확인한다. 새로고침으로 최신 접수 내용을 조회한다. ‘내 주문 · 항목 추가’로 본인 주문 또는 추가 항목을 작성하며 기존 제출을 수정하거나 삭제할 수 있다.
5. ‘참여 마감’은 최종 전송과 별개다. 마감 후 공유 링크의 GET·POST 모두 `참여할 수 없는 주문서입니다.`를 표시한다. 마감 전에 열어 둔 화면에서도 제출을 받지 않는다. 총무의 추가·수정·삭제는 계속 가능하다.
6. 마감해도 30분 폐기 시각은 바뀌지 않는다. 폐기·주문서 삭제 후에는 추가/수정도 차단한다. 주문서와 제출 내역은 보존한다. 화면에 현재 카페 전송 기능이 아직 연결되지 않았음을 안내한다.

## 데이터와 처리

- `Submission`은 닉네임·주문방·입력 경로·중복 방지 키·메뉴/옵션/수량/금액 사본·버전·시각을 보관한다. 비회원 계정, 전화번호, 이메일, 개별 IP 또는 카카오 토큰 필드는 만들지 않았다.
- 주문은 해당 방의 고정 `menu_snapshot`으로만 검증한다. 현재 원본 메뉴·옵션·품절·로그아웃 상태로 재계산하지 않는다. 이름·기본가·옵션 추가금·단가·행 금액·총액은 서버가 결정하며 브라우저가 보낸 가격은 사용하지 않는다.
- 수량은 정수 1~99잔, 제출당 1~50개 메뉴 항목, 이름은 1~30자로 검증한다. 메뉴/옵션 ID의 소속, 필수 선택, 하나 선택 그룹의 중복, 선택값 중복·형식과 허용 범위를 검사한다. 여러 선택 옵션도 지원한다.
- 모든 쓰기는 트랜잭션에서 같은 주문방 행을 잠근 뒤 진행한다. 제출·마감·삭제·폐기를 직렬화하며 잠금을 얻은 뒤 현재 시각을 확인한다. 만료를 기록한 경로는 정상 반환으로 트랜잭션을 완료해 폐기 상태가 롤백되지 않게 한다.
- 제출 화면마다 서명한 일회 제출 키를 발급한다. 키는 주문방에 묶여 있고 30분 동안만 유효하다. DB의 `(room, request_key)` 고유 제약과 행 잠금으로 더블 클릭·POST 재시도·동시 제출의 중복 접수를 막는다. 새로 연 링크에서 같은 닉네임을 다시 제출하는 것은 별도 접수다.
- 수정·삭제에는 제출 버전을 비교한다. 다른 창에서 수정/삭제된 버전은 409로 거절한다. 수정 화면은 미저장 입력을 보존한다. 새 참여자의 접수는 다른 제출의 수정과 충돌시키지 않는다.
- 항목 삭제는 `deleted_at`으로 처리하고 합계에서 제외한다. `SubmissionRevision`에는 제출·수정·삭제 시점의 내용을 기록해 이전 버전을 보존한다. 주문방 마감 이벤트는 한 번만 저장한다.
- JSON 메뉴판은 `json_script`, 동적 텍스트는 `textContent`로 전달한다. 모든 쓰기에 CSRF를 적용한다. 비회원 응답에는 제출 목록·총무 닉네임·연결코드·이력을 포함하지 않는다. 운영자는 전체 주문서를 조회할 수 있지만 다른 총무의 항목을 편집할 수 없다. 판매자에게는 개인별 취합 화면을 허용하지 않는다.
- 기본 배포 방식·외부 로그인 설정·패키지·플랫폼은 변경하지 않았다. 추가 테이블 마이그레이션만 적용하며 기존 카페·회원·주문방 데이터와 사본은 유지한다.

## 검증

- 실제 PostgreSQL 전체 테스트 **84개 통과**. 이 단계 신규 19개 테스트는 금액·옵션·수량·닉네임 검증, 가격 조작 무시, 기본값, 원본 변경 후 사본 유지, 중복 방지, 권한·CSRF·개인정보 비노출, 30분 경계의 실제 상태 변경, 마감·삭제·수정 충돌과 보존을 포함한다.
- 별도 DB 연결의 두 스레드로 같은 제출 키, 서로 다른 참여자, 제출/마감 경합, 같은 버전의 동시 수정을 검증했다. 같은 키는 한 건, 서로 다른 제출은 모두 보존, 동시 수정은 하나만 성공한다.
- Chromium **320·390·1440px**에서 실제 CSRF 폼으로 동일 메뉴의 서로 다른 옵션과 다른 메뉴를 함께 제출했다. 원본 가격이 바뀌어도 방의 가격을 사용하며 기본값/추가금과 합계가 서버 DB 결과와 일치했다. 제출 후 새로고침, 수정값 재표시, 409 입력 보존, 마감 전에 열린 폼 제출 차단, 마감 후 총무 추가/삭제를 확인했다. 가로 넘침과 JavaScript 오류가 없었다.
- 로컬 검수 회원·세션·카페·메뉴·주문방·제출·수정 이력은 검수 후 제거했다. Railway에는 가짜 주문이나 검수 계정을 만들지 않는다.
- Ruff, 형식, JavaScript 구문 검사, 마이그레이션 차이 없음, PostgreSQL 쓰기/읽기를 확인했다.

## 주문서·메뉴 선택 UI 보완 — 2026-10-21

- 주문서 제목을 한국 시각 기준 생성 시각 `HH:MM 주문서`로 바꾸고 바로 아래에 공유 링크와 겹친 네모 SVG 복사 버튼을 배치했다. 기존 ‘주문서 상태’ 카드와 장문 설명을 제거하고 마감/폐기/삭제 안내만 간결하게 표시한다. 모인 주문·편집·마감 기능은 유지하고 메뉴판·처리 이력은 접어서 표시한다. 마지막에는 카페 이름·주소·전화번호·자동 폐기 시간을 둔다.
- 복사는 HTTPS Clipboard API와 선택 복사 대체 경로를 지원하며 성공/실패를 알린다. 읽기 전용 링크의 전체 값을 복사한다.
- 주문방에 고정된 메뉴의 분류로 탭을 만든다. 분류가 없으면 ‘기타’에 모으며 원본 분류 변경으로 기존 방의 탭을 바꾸지 않는다. 탭은 클릭·방향키·Home/End로 전환하고 선택한 분류의 메뉴만 표시한다. 메뉴 행은 메뉴명·그 아래 가격·담기 버튼으로 간결하게 배치한다.
- 기존 옵션 하단의 입력칸은 음료 수량이었다. 음료 수량은 메뉴명 옆으로 옮기고 `multiple` 옵션에는 선택 항목마다 오른쪽에 별도 수량을 제공한다. 선택하지 않은 옵션의 입력은 비활성화한다. 하나 선택 옵션은 기존 라디오를 유지한다. 메뉴를 담으면 메뉴명·음료 수량이 보이는 위치로 이동하고 옵션에 초점을 두어 숫자 키보드가 먼저 열리지 않게 한다.
- 옵션 수량은 음료 한 잔당 추가 수량이다. `(메뉴 기본가 + 각 옵션 단가 × 옵션 수량의 합) × 음료 수량`으로 서버와 브라우저가 계산한다. 예를 들어 기본 3,000원에 500원 샷 2개, 200원 시럽 3개를 넣고 음료 3잔이면 13,800원이다.
- 제출 JSON의 `option_quantities`는 그룹/선택 항목별 1~99 정수 수량을 받는다. 선택하지 않은 항목·다른 그룹·하나 선택 그룹의 수량, 0/음수/소수/문자/범위 초과를 거절한다. 저장 사본에는 2개 이상 선택한 항목의 수량을 추가하고 총무 내역과 수정 폼에 복원한다.
- 기존 제출과 요청은 옵션 수량을 1로 해석한다. 1개 선택의 기존 사본 모양과 중복 제출 판정이 그대로 유지되므로 기존 주문을 재작성하거나 수정하지 않는다. DB 마이그레이션과 카페 원본 메뉴 변경은 없다.
- 전체 PostgreSQL 테스트 **89개 통과**. 옵션 수량 금액/수정 복원/기존 요청 호환/잘못된 수량 차단과 고정 분류·주문서 제목 테스트를 추가했다. Chromium 320·390·1440px에서 네 옵션 그룹의 샷/시럽 개별 수량, 실제 제출/수정 금액, 옆 칸 배치, 분류·키보드 전환, 간결한 메뉴 행, 링크 복사와 대체/실패 경로, 가로 넘침 없음·JavaScript 오류 없음을 확인했다. 검수 데이터는 로컬에서만 사용하고 제거했다.
