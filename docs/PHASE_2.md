# 2단계 — 계정·권한

작업일: 2026-10-20. 사용자가 2단계 진행을 승인했다. 주문방·메뉴·주문·알림 기능은 이번 단계에 포함하지 않는다.

## 구현 범위

- django-allauth 65.20.0의 카카오 OAuth 인증 코드 흐름을 사용한다. 로그인 시작·로그아웃은 CSRF가 적용된 POST만 허용한다. 서버가 로그인 입구의 역할을 일회성·10분 만료 OAuth 상태에 묶는다.
- 카카오 로그인 ID와 닉네임을 서비스 회원에 연결한다. 반환 데이터는 DB 조회·갱신 전 닉네임만 남기고 정리하며 이메일·프로필 사진·전화번호·인증 토큰을 저장하지 않는다. 닉네임이 바뀌어도 같은 카카오 ID면 같은 회원이다.
- 모든 회원은 총무 기능을 기본 이용한다. 운영자 권한과 카페 판매자 연결은 서버가 별도로 관리한다. 회원가입 때 역할을 골라 권한을 얻는 구조가 아니다.
- 사용자 실계정 로그인 확인 후 화면을 정리했다. 로그인 상태에서 홈은 기본 주문 화면으로 이동한다. 상단 역할 표시·화면 전환 메뉴를 제거하고 하단에 권한 있는 계정만 `판매자 페이지 이동`·`운영자 페이지 이동`을 표시한다. 판매자 이동은 CSRF가 적용된 기존 POST 입구를 사용해 영업 시작과 연결하며 일반 화면 조회는 영업을 시작하지 않는다.
- 한 카카오 회원이 세 역할을 함께 사용할 수 있다. 운영자 카페 등록·판매자 계정 연결/변경/해제 기능과 총무·판매자·운영자 화면을 분리했다.
- 판매자 입구의 유효한 로그인만 카페를 영업중으로 만든다. 총무/운영자 입구와 단순 판매자 화면 조회는 영업 상태를 바꾸지 않는다. 판매자로 들어간 세션에서 명시적으로 로그아웃하면 영업종료가 된다.
- 영업 상태와 계정 연결 변경은 DB 트랜잭션·행 잠금으로 처리하고 연결/해제/영업 시작/종료 이력을 남긴다. 카페와 판매자는 MVP에서 1:1이다.
- 유지되는 1년 세션을 매 요청 갱신한다. 카카오 토큰 갱신에 의존하지 않으며 브라우저/PC 연결 감지는 하지 않는다.
- 최초 운영자는 로그인 후 본인의 계정 연결 코드를 확인해 Railway의 `INITIAL_OPERATOR_ACCOUNT_CODE`에 지정하고 본인 계정으로 재로그인한다. 기존 운영자가 없는 경우에만 해당 계정을 지정한다. 확인 후 변수를 삭제한다. 첫 가입자 자동 승격이나 공개 권한 부여 URL은 없다. 개발 담당자의 복구용 `grant_operator` 관리 명령도 제공한다.
- Gunicorn 접근 로그에서 쿼리 문자열을 제외해 카카오 콜백의 인증 코드·상태를 남기지 않는다.

## 외부 연결

[카카오 설정 가이드](KAKAO_SETUP.md)의 앱 소유자 설정과 실제 키 등록이 필요하다. 키가 없으면 로그인 버튼을 비활성화하고 직접 인증 요청은 503으로 차단한다. 가짜 카카오 로그인이나 공개 테스트 계정 입구는 만들지 않는다.

## 검증 상태

- 실제 PostgreSQL에서 Django 테스트 31개 통과. OAuth 콜백 응답은 네트워크 대역으로 모사했다.
- 포함한 검증: 잘못됨/만료/재사용 상태 거절, 잘못된 인증 대상·추가 scope·외부 이동 파라미터 무시, 두 로그인 탭의 역할 구분, 같은 ID 재로그인 시 계정 중복 방지, 닉네임 갱신, 추가 개인정보·토큰 미저장, 이용 중지 계정 차단.
- 역할별 접근 제한, 한 계정의 세 역할, 판매자 입구에서만 영업 시작, POST/CSRF 로그아웃, 판매자 연결/변경/해제 후 권한 회수·영업종료, 이미 연결된 계정의 중복 카페 연결 방지, 닉네임 HTML 이스케이프, 운영자 지정 명령을 검증했다.
- 사용자가 닉네임 동의항목을 설정한 뒤 실제 카카오 로그인 성공을 확인했다. 운영자·판매자 계정 연결과 실계정 세 역할 검수는 남아 있다.
- 로컬 Chromium 320px·390px·1440px에서 메인·판매자/운영자 입구·총무/판매자/운영자 화면을 확인했다. 실제 POST로 판매자 영업 시작·로그아웃 종료를 확인했고 가로 넘침이 없었다. 로컬 화면 검수에만 사용한 임시 회원·카페·세션은 삭제했다.
- 운영 설정 검사에서 DEBUG·HTTPS 리다이렉트·Secure 세션/CSRF 쿠키 설정을 확인했다. HSTS는 테스트 호스트에 1시간만 적용하며 공유 도메인의 하위 도메인 확장·preload는 적용하지 않아 해당 두 권고는 남겨 둔다.
- Docker는 비특권 실행을 유지한다. 의존성은 읽기/실행만 하면 되므로 전체 가상환경의 소유권을 재귀 변경하지 않고 출력 디렉터리의 부모 `/app`만 소유권을 변경해 빌드 시간을 줄였다.
- Railway 배포 `9546eb23-fcc3-4aaa-b21d-1228881b7574` 상태 `SUCCESS`. 실제 HTTPS의 세 로그인 입구 200, 보호 화면의 비로그인 접근 제한, CSRF 없는 로그아웃 차단, 비밀번호 가입 경로 부재, 미설정 카카오 인증 차단, 새 CSS·DB 준비 상태 200, Secure 쿠키를 확인했다.
- 이후 사용자가 실제 카카오 설정을 등록했다. 당시 서버가 읽던 `KAKAO_REST_API_KEY`로 변수 이름을 맞추면서 기존 값을 유지했고 재배포 `dafe679b-ce4d-492b-8e0c-26818b19c380`가 성공했다. 로그인 버튼 활성과 카카오 인증 요청 302·정확한 콜백·닉네임 scope·OAuth 상태를 확인했다. 이어 사용자 요청으로 서버의 기본 변수 이름을 `KAKAO_RESET_API_KEY`로 변경했고 기존 이름은 배포 중 호환용으로 지원한다. 이후 사용자 본인의 실제 로그인은 확인됐고 운영자·판매자 연결은 코드 확인 대기다.

## 다음 범위

사용자 카카오 로그인 확인 후 개인정보 페이지를 요청대로 추가했다. 상단 닉네임으로 접근하며 연결코드는 이 페이지에서만 표시한다. 사용자 승인으로 [3단계](PHASE_3.md) 메뉴·옵션·카페 연락처와 주문방 생성·메뉴판 고정·30분 폐기를 진행했다. 본인 코드 확인 후 실제 운영자·판매자 연결 검수는 남아 있다.
