# 3단계 — 메뉴와 주문방

사용자가 개인정보 페이지 수정 후 다음 단계 진행을 요청했다. 3단계 범위는 카페·메뉴·옵션 관리, 고정 메뉴판 주문방과 30분 폐기다. 참여자의 음료 제출·총무 수정·마감은 4단계, 최종 전송과 5분 자동 거절은 5단계다.

## 구현

- 상단 닉네임은 `/accounts/profile/`로 이동한다. 본인 닉네임·가입일·연결코드와 본인 주문 이력을 표시한다. 연결코드는 기본 주문 화면과 권한 안내 화면에서 제거했다. 개인정보는 로그인 필수·캐시 금지이며 다른 회원을 지정하는 요청값을 받지 않는다.
- 운영자는 카페 전화번호·주소와 메뉴 이름·분류·원 단위 가격·노출 여부를 관리한다. 메뉴 사진은 없다. 메뉴에 기본 아이스/핫·샷 +0 옵션을 생성하고 운영자가 수정·삭제할 수 있다.
- 옵션은 하나/여러 개 선택, 필수 여부, 선택 항목별 추가 금액·기본값을 지원한다. 하나 선택의 기본값 중복·빈 항목 목록·중복 항목 이름·음수 가격을 거절한다. 조건부 옵션은 없다.
- 판매자는 자기 카페의 메뉴 품절만 변경한다. 가격·옵션·카페 정보 변경 권한은 없다. 신규 링크는 영업중 카페와 주문 가능한 메뉴가 있을 때만 생성한다. 품절·로그아웃 이후에도 이미 생성된 방의 메뉴판은 유지한다.
- 주문방 생성과 메뉴 변경·품절·영업 변경을 동일한 카페 행 잠금으로 직렬화한다. 방 생성 시 메뉴·옵션·가격·기본값·카페 연락처를 JSON으로 보관한다. PostgreSQL 트리거로 메뉴판·카페 사본·참여 토큰·생성/만료 시각 변경을 차단한다. 기존 방을 다시 열어도 원본 메뉴로 교체하지 않는다.
- 참여 주소는 예측하기 어려운 192비트 토큰을 사용한다. 비회원 응답에는 공유 메뉴만 제공하며 총무 닉네임·계정 코드·처리 이력을 포함하지 않는다. 현재는 메뉴 확인까지 가능하고 참여자 제출은 다음 단계다.
- 생성 직후 정확한 폐기 시각을 안내한다. 미전송 주문방은 생성 30분 뒤 폐기한다. 총무 삭제는 물리 삭제가 아니며 원본 메뉴판·생성/폐기/삭제 이벤트를 보존한다. 종료된 링크에는 `참여할 수 없는 주문서입니다.`를 표시한다.
- 기본 주문 화면은 진행 중인 주문서만 보여 준다. 개인정보의 주문 이력은 본인 모든 상태를 최신순·20개씩 조회한다. 운영자는 최근 전체 주문서를 조회할 수 있으나 다른 총무의 주문서를 삭제할 수 없다.

## 자동 처리와 실행

`manage.py run_deadlines`는 5초 간격으로 기한을 처리한다. 화면 요청에서도 기한을 검사하므로 정확한 30분 경계 이후에는 참여할 수 없다. DB 상태는 백그라운드 처리 주기 내에 갱신된다. 행 잠금·`skip_locked`·이벤트 고유 제약으로 중복 폐기를 방지한다. 재시작하면 놓친 기한을 다시 처리한다.

Railway는 기존 웹 서비스 안에서 웹과 기한 처리 프로세스를 함께 실행한다. `scripts/run_services.py`가 두 프로세스를 감독하고 하나가 비정상 종료하면 나머지도 종료해 Railway의 재시작 대상이 되게 한다. 별도 플랫폼·Redis·외부 스케줄러는 추가하지 않았다. DB 마이그레이션 후 시작하며 종료 신호를 받으면 함께 정리한다.

개발 시에는 README의 웹 서버 명령과 별도로 `.venv/bin/python manage.py run_deadlines`를 실행한다. 한 번만 처리하려면 `--once`를 사용한다. 개발 DB에서만 테스트한다.

## 검증

- 실제 PostgreSQL 테스트 **50개 통과**. 기존 카카오·역할 테스트와 개인정보 접근 제한, 메뉴·옵션 검증, 자기 카페 품절 권한, 메뉴판 불변 트리거, 기한 직전/정각/이후, 마감된 미전송 방, 삭제 이력, 중복 처리 방지, 두 처리 프로세스 경합, 감독 프로세스 실패 처리를 포함한다.
- 별도 기한 처리 프로세스를 실행해 HTTP 요청 없이 DB가 폐기 상태로 변하는 것을 확인했다. 재시작 후 이벤트가 중복 생성되지 않았다. 30분 전체를 기다린 실기기 검수가 아니라 생성 시각을 조정해 실제 기한 경과와 프로세스 동작을 확인한 검증이다.
- 실제 `scripts/start_web.sh` 실행에서 DB 준비 응답, 기한 처리 시작, 종료 신호 시 정상 종료를 확인했다. Railway 배포에서도 새 프로세스 시작 로그와 HTTPS 응답을 확인했다.
- Chromium 320·390·1440px에서 기본 주문·개인정보·판매자·운영자·카페 관리·옵션·주문서 화면에 가로 넘침이 없었다. 실제 CSRF POST로 메뉴/옵션 저장, 영업 시작, 링크 생성, 원본 가격 변경 후 기존 참여 메뉴 유지, 이력 조회, 삭제, 로그아웃을 확인했다. 임시 회원·카페·세션·주문서는 로컬에만 만들었고 검증 후 제거했다.
- Ruff 검사·형식 검사·마이그레이션 차이 없음·실제 DB 쓰기/읽기 검증을 통과했다.

## 남은 확인

사용자 카카오 로그인은 확인됐다. 본인이 확인해 전달한 연결코드로 운영자·판매자 권한을 연결했다. 관리 명령의 정상 종료와 배포 성공을 확인했으며 일회성 배포 전 명령은 원복했다. 실계정에서 판매자 페이지 이동·로그아웃을 누르는 브라우저 검수는 사용자 확인 대기다. 닉네임이나 첫 가입자라는 이유만으로 운영자 권한을 부여하지 않는다. 테스트 권한 연결용 관리 명령 `setup_test_account`는 활성 카카오 계정만 허용하며 다른 운영자가 이미 있으면 거절한다. 기존 판매자 카페가 있으면 유지하고, 없으면 `영차 테스트 카페`를 연결한다. 계정 연결만으로 영업을 시작하지 않는다.

4단계 참여자 제출·총무 취합과 이후 최종 전송·판매자 주문 처리·알림은 구현하지 않았다. 실제 카페 주문에 사용하지 않는다.

테스트 배포: `648069c2-1fb5-475b-8ce3-7a72e5bf3927` (`SUCCESS`). 개인정보 주소: https://coffegroup-web-production.up.railway.app/accounts/profile/

개발환경의 `start_skill` 초안도 웹과 기한 처리 프로세스를 함께 시작하도록 갱신·저장했다. 이 초안은 환경 설정에서 검토·저장 후 환경을 게시해야 새 작업 환경에 적용된다. Railway 사이트 배포는 별도로 이미 완료했다.

후속 배포 `3b1a9ab6-9021-476d-87f4-d1199413a65b`: 개인정보의 겹친 네모 아이콘 버튼으로 본인 계정 코드를 복사한다. 실제 클립보드·대체 경로·실패 안내와 320·390·1440px 화면을 확인했다. 버튼·상태 안내는 개인정보에만 포함하고 JS는 이 페이지에서만 로드한다.

후속 4단계에서 참여자 주문 제출·총무 취합·편집·마감을 구현했다. 최신 범위와 검증은 [4단계 기록](PHASE_4.md)을 참고한다.
