# 8단계 — 카페 시험 운영 준비

사용자가 2026-10-23 진행을 승인했다. 이후 사용자 안내에서는 ‘파일럿’ 대신
‘협력 카페 한 곳에서 실제 주문을 받아 보는 시험 운영’이라고 설명한다.
이 단계는 진행 중이며 실제 카페 이용자를 받기 위한 준비 완료로 보고하지 않는다.

## 먼저 확인한 내용

- 기존 주문·권한 테스트와 7단계의 실제 300초 기한 검증 결과는 유지된다.
  실제 Google에서의 장시간 무접속 기한 처리와 재시작·복원 확인은 별도다.
- 운영 설정을 적용한 Django 보안 검사에서 HTTPS·쿠키·비밀키 관련 필수 경고는
  없었다. 공유 Google 주소 전체의 하위 주소/HSTS preload에 관한 두 권고는
  의도적으로 적용하지 않았다. 검사를 통과했다고 보안 문제 전체가 없다는 뜻은 아니다.
- 앱의 웹 접속 로그는 쿼리 문자열을 출력하지 않는다. Google 플랫폼이 별도로
  보관하는 요청 로그·보유기간·접근 권한은 실제 Google 설정 확인이 남아 있다.
- 카카오 계정 구분 번호와 닉네임, 가입·로그인 시각과 자체 계정 연결 코드를
  저장한다. 이메일·전화번호·프로필 사진·카카오 액세스 토큰은 수집·저장하지 않는다.
- 비회원은 자유 입력 닉네임·주문·옵션·수량·시각·중복 제출 방지용 번호를 저장한다.
  서버 접속 기록과 회원/주문 DB의 자료 범위를 구분해 안내해야 한다.
- 주문의 영구 보존과 계정 개인정보 보유·파기는 별도 기준이 필요하다.
  회원 탈퇴 화면과 카카오 연결 해제 처리, 주문 사본에 남은 닉네임의 처리 방식은
  아직 구현/확정되지 않았다. 동의 체크박스가 반드시 필요하다고 미리 정하지 않는다.
  [실제 보유 항목과 남은 결정](PRIVACY_PREPARATION.md)을 참고한다.

## 완료한 복원 연습

실제 운영 자료를 사용하지 않는 로컬 PostgreSQL의 별도 연습용 DB에서 다음을 확인했다.

1. 수락·거절·메뉴 완료·알림을 포함한 가짜 주문을 만들고 실제 pg_dump 백업을 생성했다.
2. 또 다른 빈 연습용 DB에 pg_restore로 복원했다.
3. 27개 표의 모든 행 수와 전체 내용의 SHA-256 비교값이 일치했다.
4. 복원된 DB에서도 최종 주문·고정 메뉴판의 수정 방지 규칙이 작동했다.
5. 연습용 원본·복원 DB를 정리했다. 개발 DB와 Google 자료는 변경하지 않았다.

도구는 `scripts/verify_backup_restore.py`다. 로컬 DB만 허용하며 원격 주소에서는
실행을 거부한다. 이 성공이 Google의 PostgreSQL 18 백업·복원 성공을 뜻하지 않는다.

## 다음 실제 Google 확인

이 환경에는 Google 계정 인증이 없다. 사용자가 기존 Cloud Shell에서 다음을 실행한다.

```bash
git -C ~/yeongcha pull --ff-only && python3 ~/yeongcha/scripts/gcp_inspect_operations.py
```

이 도구는 웹/DB 설정, 자동 백업과 최근 백업 성공 기록, 삭제 방지, 상시 실행 설정,
최근 오류 기록의 시각·심각도와 HTTPS/DB 준비 상태만 조회한다. 비밀값을 가져오거나
로그 본문·사용자 자료·결제 계정 번호를 출력하지 않는다. 실제 요금/크레딧 잔액과
복원 성공 여부를 확인했다고 보고하지 않는다. 이 동작을 확인하는 4개 검사에 통과했다.

조회 결과에 맞춰 Google 백업 생성·격리된 복원 확인·복구 절차, 오류 점검과
비용 확인을 이어간다. 기존 상시 CPU·최소 1대 구성은 사용량이 적어도 비용이
발생하므로 크레딧 종료 후 월 5만 원 예산 충족을 아직 확정하지 않는다.
기한 처리를 검증하지 않고 최소 인스턴스/CPU를 줄이지 않는다.

개인정보 안내에 공개할 운영 주체명과 문의용 이메일을 사용자에게 요청했다.
이 정보와 보관·파기 기준이 정해지기 전에 임의의 운영자 정보나 법정 보유기간을
꾸며 사이트에 게시하지 않는다. Google 확인 결과와 남은 개인정보 처리를 마친 뒤
실제 주문 전체 흐름을 확인하고 카페 시험 운영 시작 여부를 사용자에게 보고한다.


## Google 현재 설정 확인 결과 — 2026-10-23

사용자가 조회 도구의 실제 실행 결과를 전달했다.

- 웹 yeongcha-test-00010-4jv와 DB는 정상 준비 상태다. 로그인·운영 설정과
  네 개 비밀값 참조가 유지되고 임시 운영자 지정 변수는 없다.
- 서울에서 1 CPU/512Mi, 최소/최대 1개, 상시 CPU로 실행한다. 비용 확인은 남아 있다.
- Cloud SQL PostgreSQL 18, db-f1-micro, 10GB, 단일 영역이다.
- 자동 백업이 켜져 있으며 7개를 보관한다. 시작 설정 UTC 18:00은 한국 시간
  매일 오전 3시다. 2026-10-22 18:13:06~18:14:27 UTC의 자동 백업이 성공했다.
- 외부 IP 직접 접근 허용 항목은 0개다. 최근 24시간 조회한 ERROR 이상 기록은 0개이며
  이를 모든 종류의 오류나 장애가 없다는 의미로 확대하지 않는다.
- 삭제 방지는 꺼져 있고 특정 시점으로 복구하는 기능은 꺼져 있다. 현재 백업에서
  실제 Google 별도 공간으로 복원하는 검증은 아직 수행하지 않았다.

다음은 기존 DB의 삭제 방지를 켜는 단계다. 데이터 삭제·DB 교체·CPU 변경을 하지 않는다.
사용자가 실행할 정확한 명령:

```bash
gcloud sql instances patch yeongcha-db --deletion-protection --project=active-venture-449808-a5
```

이 보호 설정의 적용 결과를 확인하고, 현재 시점의 별도 백업과 운영 DB와 분리한
복구 검증을 준비한다. 오래된 자동 백업만으로 최근 변경의 복구까지 확인했다고
보고하지 않는다. Google의 실제 복원과 비용·개인정보 준비는 계속 미완료 상태다.


## 2026-10-24 삭제 보호와 수동 백업 확인

사용자가 삭제 방지 설정 성공 출력을 전달했다. 현재 yeongcha-db의 삭제 방지는 켜져 있다.

사용자가 요청한 수동 백업은 ID `1792849041384`, ON_DEMAND, SUCCESSFUL이다.
설명은 yeongcha-recovery-check-20261023이고 완료 시각은
2026-10-24 13:38:42.417 UTC(한국 시간 22:38:42)다. 설명의 날짜와 실제 완료일은 구분한다.

다음은 원본과 다른 이름의 빈 임시 저장소를 만드는 단계다. 기존 사이트 연결,
원본 삭제 보호와 계정·자료를 변경하지 않는다. 임시 자원에도 실행 시간에 따른
비용이 발생하므로 복원·검증 뒤 삭제한다. 아직 임시 자원은 만들지 않았다.

```bash
gcloud sql instances create yeongcha-restore-check-20261024 --database-version=POSTGRES_18 --edition=ENTERPRISE --tier=db-f1-micro --region=asia-northeast3 --availability-type=zonal --storage-size=10GB --async --project=active-venture-449808-a5
```

생성 상태가 RUNNABLE인지 확인한 다음에만 백업을 위 임시 대상으로 복원한다.
복원 명령의 대상(restore-instance)에 원본 yeongcha-db를 넣지 않는다.
현재 Google 복원 실행·복원 자료 읽기/쓰기·임시 자원 정리는 여전히 미완료다.

### 생성 명령 정정

사용자의 일반 `gcloud sql instances create`는 `--labels`를 지원하지 않아
명령 해석 단계에서 거부됐다. 이 시도에서 자원은 생성되지 않았다.
위 명령에서 해당 옵션을 제거했다. 이미 원본을 생성할 때 사용한 일반 명령의
지원 옵션만 사용하며, 이 이유로 alpha/beta 명령으로 전환하지 않는다.
임시 자원은 정확한 별도 이름과 사용자의 생성 결과를 확인해 관리한다.

## 2026-10-25 실제 Google 복원 완료·자료 검사 준비

사용자가 실제 작업 조회 결과를 전달했다. 임시 저장소 생성 작업
be8083d2-5680-4327-8fab-5bd600000042는 2026-10-24 14:06:37.903 UTC에
오류 없이 끝났다. 백업 복원 작업 8cf98307-cb42-4183-a620-e55100000042는
RESTORE_VOLUME, DONE, 오류 없음이며 2026-10-24 14:47:10.694~15:00:10.772 UTC에
수행됐다. 약 13분으로, 한국 시간 완료 시각은 2026-10-25 00:00:10이다.
Cloud Shell 화면 연결이 끊겨 완료 출력을 못 본 상황이며 복구를 다시 요청하지 않는다.

scripts/gcp_check_recovery.py는 이 정확한 복원 작업 번호와 대상 연결 이름·준비 상태를
확인한 뒤 별도 Cloud Run Job으로만 복원된 DB를 검사한다. 실행 중인 사이트의
설정을 갱신하지 않는다. 같은 배포 이미지와 기존 비밀값 참조를 사용하되 임시
Cloud SQL 소켓만 연결하고, DB 연결 설정도 임시 대상으로 고정한다.

검사는 적용된 DB 구조, 기존 회원·카페·메뉴와 주문 표 조회, 주문 수정 방지 규칙,
임시 값 저장·읽기를 확인한다. 마이그레이션·기한 처리·원본 주문 수정을 실행하지 않는다.
개인정보나 비밀값을 화면에 출력하지 않고, 검사 성공 후에만 임시 Job과 임시 SQL
저장소를 제거한다. 원본 삭제 방지를 해제하지 않는다. 임시 자원이 이미 삭제된 경우
정리 명령을 다시 실행해도 원본이나 다른 자원을 삭제하지 않는다.

로컬 검증: 명령 순서·격리·오대상 차단·실패 처리·정리 반복·다른 소유 Job 보호 6개,
실제 PostgreSQL 구조·조회·임시 쓰기와 연결 강제 분리 검사 2개 통과.
이는 Google에서 자료 검사까지 통과했다는 의미는 아니다. 실제 실행 명령:

```bash
git -C ~/yeongcha pull --ff-only && python3 ~/yeongcha/scripts/gcp_check_recovery.py
```

검사가 실패하거나 연결이 끊겨 임시 공간이 남으면 결과를 먼저 확인한다.
별도 정리만 필요할 때는 같은 스크립트의 `--cleanup-only`를 사용할 수 있다.
정리가 확인될 때까지 임시 SQL 비용이 발생할 수 있다. 실제 요금과 개인정보 준비는
계속 남아 있다. 사용자가 전달한 Google 검사/정리 성공 출력 전에는 완료로 보고하지 않는다.
