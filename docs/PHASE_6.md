# 6단계 — 판매자 합산 주문 조회·수락·거절

사용자가 6단계 시작을 승인했다. 이번 승인 범위는 자기 카페 합산 주문 조회,
5분 단위 완료 예정시간과 수락, 1~30자 사유를 포함한 거절, 총무 화면 결과 반영이다.
PC 반복 소리·소리 테스트·일반 웹 알림은 7단계로 남긴다. 준비/픽업 완료 상태나
완료 예정시간 변경 기능은 이번에 추가하지 않았다.

## 사용 흐름

1. 기존 판매자 입구로 로그인하면 기존 방식대로 카페가 영업중이 된다.
   별도 영업 중지 버튼·연결 감지·새 계정 설정은 추가하지 않는다.
2. 판매자 페이지는 수락 대기, 접수한 주문, 거절·취소 내역과 기존 품절 관리로
   구성한다. 수락 대기는 전부 표시하며 접수/종료 내역은 각 20개씩 조회한다.
3. 전송된 고정 주문서에서 같은 메뉴·옵션을 합친 수량·금액과 총무 닉네임만
   보여 준다. 옵션 그룹 이름과 선택값·잔당 옵션 수량을 함께 표시한다.
4. 수락 시 완료 예정시간을 반드시 선택하고 ‘주문 접수’를 누른다. 선택지는
   현재 다음 5분 경계부터 24시간 동안이며 자정을 넘으면 ‘내일’을 표시한다.
   서버는 미래 시각·5분 경계·초/마이크로초 0을 다시 검사한다. 선택지의
   24시간 범위는 표시 범위이며 별도 예약 주문 기능이 아니다.
5. 거절을 펼쳐 1~30자의 사유를 입력하고 ‘거절하기’를 누른다. 공백만 있거나
   너무 긴 사유·제어 문자는 거부하고 HTML은 화면에서 이스케이프한다.
6. 총무가 열어 둔 수락 대기 주문서는 기존 상태 조회로 자동 갱신해 수락과
   고정 완료 예정시간, 또는 거절 사유를 표시한다. 수락 뒤에는 취소할 수 없다.
7. 판매자 화면도 5초 간격으로 변화를 확인한다. 새 주문/처리 결과가 바뀌면
   갱신하며, 작성 중인 입력은 유지하고 갱신 안내를 표시한다. 이미 취소·수락·
   거절된 대기 항목은 입력 중이어도 제거해 잘못 처리하지 않도록 한다.

## 데이터·권한·시간 경계

- `Room.ready_at`만 추가하고 기존 `resolved_at`에 판매자 결정 시각을 기록한다.
  `accepted`, `seller_rejected` 처리 이력을 기존 append-only 이력에 추가한다.
  기존 최종 메뉴·가격·옵션·수량·합계 사본은 다시 쓰지 않는다.
- 판매자 응답은 명시적인 허용 필드 사전으로 만든다. Room/회원/참여자 모델을
  템플릿에 넘기지 않고, 참여자 이름·주문별 내역·공유 토큰·회원 연결코드·
  총무 전화번호·메뉴/옵션 내부 ID를 제외한다. 알림용 상태 응답도 버전과
  자기 카페의 대기 주문 ID만 포함하며 no-store다.
- 요청의 로그인·활성 계정·카페 연결을 검사하고 결정 직전에 Room → Cafe
  순서로 잠근 뒤 현재 판매자와 영업중 상태를 다시 확인한다. 운영자 권한만으로
  판매자 결정을 대신할 수 없다. 한 계정이 총무와 연결 판매자를 겸하는 것은 가능하다.
- 같은 Room 잠금으로 수락·거절·총무 취소·자동 거절을 직렬화한다. 정확히
  전송 5분이 지났으면 자동 거절을 먼저 커밋한다. 이미 처리한 주문의 반복
  요청은 완료 예정시간·사유·결정 시각을 바꾸거나 이력을 중복 추가하지 않는다.
- 수락 상태에서만 완료시간을 허용하고 그 값이 결정 시각 이후인지 DB 제약으로
  검사한다. 기존 상태 보호 트리거를 확장해 5분 경계와 완료 예정시간 변경 금지도
  DB에서 검사한다. 기존 최종 주문·접수·수정 이력의 보호 트리거는 유지한다.
- 이력 버전은 자기 카페 최종 주문의 처리 이벤트 수와 가장 큰 ID로 계산한다.
  초기 목록보다 먼저 읽어 동시 도착을 다음 조회에서 놓치지 않도록 한다.
  이벤트가 서로 다른 트랜잭션에서 순서와 다르게 커밋돼도 건수 변화로 감지한다.

## 검증

- 전체 PostgreSQL 테스트 **153개 통과**. 신규 28개는 카페별 조회/개인정보 제외,
  같은 계정의 총무·판매자, 완료시간/거절 사유 검증, 정확한 5분 경계,
  반복/상충 요청, 이력/사본 보존, DB 직접 수정 방지, 롤백과 페이지 조회를 포함한다.
- 독립된 DB 연결로 수락/취소, 수락/거절, 이중 수락, 5분 정각 결정/워커,
  로그아웃/수락, 판매자 연결 해제/수락을 동시에 실행해 한 결과만 남는지 확인했다.
- 일회용 DB와 실제 HTTP/CSRF·서로 다른 총무/판매자 브라우저 세션에서
  320·390·1440px 합산 주문 조회·개인정보 비노출·새 주문 자동 표시·수락/고정 시간·
  거절 사유·총무 자동 갱신·취소·작성 중 입력 유지·가로 넘침 없음을 확인했다.
- 기한을 단축하거나 전송 시각을 수정하지 않고 실제 **300초**를 기다렸다.
  기한 전에는 대기를 유지하고 이후 DB가 ‘주문 거절 · 5분 미응답’이 됐다.
  입력 중이던 판매자 대기 카드도 사라지고 거절 내역에 사유가 나타났다.
  거절 이력은 한 번, 최종 사본과 시각은 그대로였고 수락한 주문은 유지됐다.
- 최종 화면을 별도로 검사해 PC의 시간 선택/접수 버튼 한 줄 배치, 모바일 줄바꿈,
  Noto Sans KR, 유효하지 않은 POST 뒤 입력 보호, 실제 CSRF 접수를 확인했다.
- Ruff·형식·JavaScript 구문·마이그레이션 차이 없음·개발 DB 마이그레이션 및
  쓰기/읽기 검사가 통과했다. 검수 DB와 프로세스는 정리했으며 실제 Railway에
  가짜 주문·회원이나 로그인 우회 경로를 만들지 않았다.

## 배포

기존 Railway 웹·PostgreSQL·기한 처리 프로세스를 사용한다. 마이그레이션 0006은
nullable 완료시간과 제약·이력 선택지를 추가하고 0007은 상태 보호 함수를 확장한다.
기존 5단계에는 실제 판매자 수락 경로가 없었다. 새 런타임 전 마이그레이션을
적용하며 이전 런타임의 미전송 생성·취소·자동 거절과 호환된다. 새 환경변수나
카카오 설정·알림톡·외부 작업 큐·유료 서비스를 추가하지 않는다.

배포 후 실제 마이그레이션과 웹/기한 처리 시작, 공개 HTTPS·정적 파일·인증/CSRF를
확인한 뒤 아래에 결과를 기록한다. 반복 소리·알림 테스트·앱 푸시 성공으로
보고하지 않는다. 앱 단계의 Apple APNs·Google FCM 결정은 유지한다.

### 실제 배포 시도 — Railway 장애로 대기

두 차례 CLI 요청이 `UPLOAD_FAILED: Deploys have been paused temporarily`로
차단되어 새 배포 ID는 생성되지 않았다. 이번에는 Railway 공식 상태 API도
`isStable: false`, `INVESTIGATING`, `Builds are temporarily paused`를 반환했다.
공식 장애: https://status.railway.com/incident/QH8L8B3E

기존 배포 `94a3e8c3-584c-4d7a-b90b-8b7dbe2a5fd1`는 SUCCESS이고 공개 홈·
DB 준비·생존 응답은 모두 200이다. 따라서 공개 사이트는 아직 5단계이며
마이그레이션 0006/0007도 Railway에는 적용되지 않았다. 개발/검수 DB에만 적용했다.
기존 `preDeployCommand`는 `.venv/bin/python manage.py migrate --noinput`이다.
토큰·요금제·프로젝트·서비스·환경변수는 바꾸지 않았다.

장애 해제 후 같은 서비스로 다시 업로드하고 새 배포 SUCCESS, 0006/0007 적용·
웹/기한 처리 시작, 실제 HTTPS·selling CSS/JS와 소스 일치·판매자 인증/CSRF·
기존 카카오 인증을 검증해야 한다. 공개 사이트용 비로그인 검수 스크립트도
준비했으며 실제 계정이나 주문을 만들지 않고 확인한다.


### 사용자 복구 확인 후 재시도

재시도 시각(UTC): 2026-10-21T13:24:47.649123+00:00. 공식 `platformStatus`는 여전히 `isStable: false`,
`IDENTIFIED`, `Dashboard and API unavailable, builds paused`를 반환했다.
프로젝트 ID 조회와 서비스 조회는 `Not Authorized`, 같은 프로젝트/서비스를
지정한 실제 `railway up`은 `UNAUTHORIZED`로 거부됐다. 새 배포 ID는 생성되지
않았으며 원격 마이그레이션도 실행하지 않았다. 관리 화면 접속 복구만으로
배포 API 복구가 확인된 것은 아니다.

관리 환경의 토큰 바인딩은 현재 `ready`이고 네트워크 오류 관측은 없었다.
바인딩 준비 상태는 Railway 프로젝트 권한의 유효성을 보장하지 않는다.
진행 중인 장애 영향인지 토큰/프로젝트 권한 문제인지는 이 응답만으로
확정할 수 없어 토큰 교체나 결제 변경을 요구하지 않았다.
공개 홈·생존·DB 준비 응답은 모두 200이다. 6단계는 구현/검증 완료,
배포 대기를 유지한다. API 복구 후 같은 요청을 재시도하고, 장애 해제 후에도
인증 거부가 지속되면 프로젝트 토큰의 유효성과 범위를 확인해야 한다.
